# 识图使用判据（2026-10-02 立）

> 这份文件是**行为规则**，不是参考资料。每条都由当天的实测事故换来，违反过的都在下面写着。
> 精简版同步在 `PERSONA_SPEC`（每会话注入）；这里是完整版与出处。

## 入口 · 默认先跑 `eye.py`（2026-10-02 立，**这一条优先于下面所有铁律**）

**要看一张图 —— 尤其是要看细节 —— 第一动作是跑流水线，不是自己一步步手动串工具。**

```
python eye.py <图片> --preset outfit|ocr|diff --out <报告.md>
```

它一条命令走完：**L0 算法证据**（尺寸/主色/本地 tesseract，不经模型）→ **L1 多模型并排**（百炼＋智谱＋本地 Ollama，自动跳过没配 Key 的）→ **L2 自动分歧检测**（裁判输出 一致/冲突/孤证 的 JSON）→ **L3 对每个冲突项自动裁图放大＋重问＋取色** → **L4 输出带 `[确证]/[推断]/[存疑]` 标注的报告**。

**为什么不许手动串**：`eyeprobe` / `vrecheck` / `vscore` 是三个孤立工具，手动串 = 要本工具先想起来、再记参数、再拼步骤。**忘了用的那部分，工具再好也救不了** —— 这正是 2026-10-02 之前所有翻车的共同点。

**只有三种情况才手工上**：① `eye.py` 报"存疑"、要人眼裁夺；② 需要确定性测量（`vision_pixel_diff` / `vision_colors` / `vision_ground`）；③ 要跑回归打分（`vscore.py`）。

### 两种模式怎么选（2026-10-02 晚补）

| 模式 | 命令 | 分歧检测靠谁 | 打分口径 | 什么时候用 |
| --- | --- | --- | --- | --- |
| **结构化（推荐）** | `eye.py <图> --schema <真值集id>` | **程序比对，零裁判** | **严格字面下界** | 有真值表的图（ref-a / ref-b / cute-01 / synthetic-ocr）；要可复现的结论 |
| 自由文本 | `eye.py <图> --preset outfit` | 模型裁判 | 无（只出证据等级） | 没有真值卡的新图、要开放式描述 |

**两种打分不是一回事，别混着比**：
- `eye.py --schema` 的分数是**严格下界** —— 只认字面接近（精确／包含／字符集重叠／字面相似度），**措辞不同但意思相同的也会判错**（实测：「金色藤蔓纹样」vs「金色藤蔓纹」算对，「四颗，两两对称排列」vs「四颗，2x2」算错）。
- `vscore.py` 的分数是**宽松上界** —— LLM 裁判判"实质一致"。
- ⇒ **真实水平落在两者之间**；报告里会连"模型原话 vs 真值"一起列，自己看是措辞问题还是真错。

**其他开关**：`--max-recheck N`（默认 4，冲突项多时限制复检量）｜ `--jobs N`（结构化模式并发，默认 1）｜ `--recheck-models`（默认 `dashscope,ollama`：一个稳、一个本地无限次且不限流）｜ `--budget N`（**全局时间预算，默认 420 秒**）｜ `--max-side N`（**入口降采样，默认 2000**）。

### ⏱ 大图不再跑死：时间预算 + 降采样（2026-10-03 立）

**起因**：一张 **2700×5400（14.6 MP）** 的立绘，`eye.py` **跑了 9 分钟没出任何结果**，只能中止。

**根因不是模型慢，是等待无上限**：`call()` 单次 socket 超时 **180 秒 × 重试 3 次 = 单后端最坏 540 秒**，再乘上每个放大块、每个复检项 —— 而整条流水线**没有任何"总时长"概念**，也看不出卡在哪一步。

| 修的是什么 | 怎么修 | 实测证据 |
| --- | --- | --- |
| **全局预算** | 新增 `--budget N`（默认 **420 秒**，0 = 不限）：每个阶段开跑前先问"还有时间吗" | 同一张 14.6 MP 图：**9 分钟无果 → 34 秒出报告** |
| **超时不再重试** | 超时是**终止性**失败，重试只是把等待乘 3；现在只对 429 / 5xx 重试 | 黑洞地址实测：8 秒预算 → **8.0 秒**返回（旧逻辑是 3×90 = 270 秒） |
| **单次超时受预算钳制** | 每次调用的 socket timeout = `min(90, 剩余预算)` | 一个挂住的调用**不可能**再拖垮整条流水线 |
| **入口降采样** | 新增 `--max-side`（默认 **2000**，0 = 不缩） | 2700×5400 → 1000×2000 |

>  **写死：被预算砍掉的步骤标成 `(未跑·超预算)` —— 它既不算「看不清」，也不算「否」。**
> 这跟「`--max-recheck 0` 让冲突项凭空消失」是同一个病：**静默丢失比判错更危险**。所以现在：
> ① 汇总写明「存疑 N（含未复检 M）」，并单独标出**多少项是被时间预算砍的**；
> ② 报告末尾**自动生成补跑命令**（同时放大 `--budget` 与 `--max-recheck`），照抄一条就能接着查。

> 注意： **降采样丢细节是有意的取舍**：整图缩过之后小目标（扣子／小字）更看不清 —— **要抠小东西请先裁块放大（见铁律二），别指望整图**。不想要这个取舍就 `--max-side 0`。

>  **同一批修掉的一个真 bug**：脚本往控制台打了一个 `注意：`，而 Windows 控制台是 **GBK** 码页 ⇒ `UnicodeEncodeError` **把进程当场打死**，症状看起来却像"脚本碰不了大图"。现已统一把 stdout/stderr 设成 **UTF-8 + replace**：中文输出不再乱码，任何字符都打得出来。**教训：控制台输出也要当成一个会失败的接口来对待。**

### 通用角色外观卡（`--schema character`，2026-10-02 立 · **同日 v2 升级**）

**用户原话**：「这个答题卡可以被扩大精细到一个**适用全角色的版本**」。

`vision-tools\schemas\character.json` —— **v2 共 54 项，不绑任何角色**：
整体（主色／体型／姿态／背景）→ 头面部（发色渐变／**发质**／发长／发型／刘海／发饰／**发饰样式**／眼／表情／肤色／非人头部结构）→ 上身（领型／**领形细节**／**领口花边**／领饰／**蝴蝶结结构**／露肩／衣物／**层数**／图案／**图案位置**／**边缘装饰**／**面料质感**／扣／袖／袖口）→ 腰（结构／**宽度·扣·系带**／垂饰）→ 下身（裙裤／层数／**纹路**／**每层花边**／开衩／**裙摆装饰件**／**面料**／长度）→ 围裙（形状／**花边**／图案／口袋／系带）→ 腿脚（袜／**袜口花边**／鞋／**鞋面装饰件**）→ 手与配饰。

- **它没有真值** ⇒ **只出描述、不打分**。`score_structured()` 遇无真值卡返回 `None`。
- **项数多 ⇒ token 预算要放大**：`ask_structured()` 按项数自动选 `1600`／`3200`／`4800`（固定 1600 会把长 JSON 截断、整张卡作废）。

>  **v2 的两处大改都是用户当场点的**：
> **① 补【服装设计细节】整类** —— 他的原话：「34 项还是不够精确……**基本没有服装设计上的细节，比如纹路、花边样式这类**」。v1 只有笼统的"图案"一项 ⇒ v2 加了花边样式（荷叶边／蕾丝／层数／宽窄／波浪形）、纹路内容、装饰件、面料质感、开衩、边缘装饰。**实测立竿见影**：答出「金色藤蔓与星座刺绣／中层蓝白细格纹／主裙摆荷叶边宽约 2cm 波浪形／内层白色蕾丝／腰封宽约 5cm 正面 4 颗金色圆形铆钉／鞋面白色横带+金色矩形搭扣／主裙哑光棉质衬裙轻薄纱感」。
> **② 长度类改问【图高的几分之几】，不再问"到身体哪个部位"** —— 他连纠两条：模型说"及膝"，实际在**小腿下部／脚踝上方**（还在飘动）；说"过臀、末端近小腿中部"，实际**最多到膝盖**。⇒ **模型对身体比例的判断系统性不可靠，而且两个方向都会错**。改图像参照后同一张图答出「裙摆**最下 1/5**」「发梢**下 1/3**」，**与他的判断吻合**。
>  **可复用的通则：当模型对某类"相对位置"判断不准时，换一个它更擅长的参照系，比叮嘱它"仔细看"有效得多。** 图像坐标正是模型的强项。

> 注意： **两个必须知道的坑**：
> ① **`--max-recheck 0` 早先会让冲突项在报告里凭空消失**（汇总显示"存疑 0"，而实际有 19 项冲突没查）—— **静默丢失比判错更危险**。现已修：未复检的项单列 `[存疑·未复检]`，汇总写成「存疑 N（含未复检 M）」。
> ② **同一个模型换个问法会给出不同答案**：7 项卡说"口袋里插着多支笔"，34 项卡说"无口袋内容物" —— **同一模型、同一张图、前后矛盾**。⇒ **跨卡结论不能直接拼接，冲突要标出来**。

###  用户的三条语言纪律（2026-10-02 19:5x，**照做，别自作聪明**）

1. **专业术语照用，后面用括号补一句白话**。他的原话：「**术语看不懂是我的问题，对 ai 来说肯定越准确越好啊**」。
   ⇒ 本工具曾自作聪明地把术语全换成"白边／白褶子"，**那不是人话，是垃圾描述** —— 既丢准确性又没变好懂。**正解：「门襟（衣服前面那条从上到下的开口边）有一圈白色荷叶边（波浪形的花边）」**。
2. **不许说没信息量的话**。他当场问「四个角是方的、稍微有点圆 —— 这是什么意思？」—— 那是模型"方形立领，四角略圆"的直译，**读了等于没读**。要么说清具体形状，要么别说。
3. **部位名词必须补一句"它指哪里"**。他问「上面有领子了，这个**领口**又是哪个部位的描述？」—— 名词堆在一起，读的人分不清是哪儿。**正解：「领子开口处（脖子前面领子中间那段）」**。

> 注意： **反面教训（本工具当天踩的）**：把上面第 1 条**过度执行**成"禁用一切术语" ⇒ **降低了给模型的信息准确度**，而他明确说"我的问题是暂时的，AI 的准确性是长期的"。**帮他看懂，不等于把标准降到他的当前水平。**

###  小目标必须「裁出来放大再问」（2026-10-02 19:5x 实测）

他发来一张 **52×88 像素的扣子特写**，指出"这块有 3 颗扣子，模型说 2 颗"。
- **原图上问**：模型答「**两颗**深蓝色纽扣」否
- **放大 8 倍（416×704）后再问**：模型答「**能明确数出的是 3 颗**圆形扣状物，从上到下依次分布；深藏蓝偏紫、正圆、**圆顶凸起不是扁平圆片**」是

⇒ **他数得对，模型错在"没看清"**。**而 `eye.py` 的复检是"整图切三段"，对很小的局部只会越切越小、帮倒忙** ⇒ **正确姿势：先裁出目标区域 → 放大 → 再问**（裁切放大这一步目前要手工做，未接进 L3）。

###  分层解析法（`layered.py`，2026-10-02 20:2x · **用户提出的方法论，当晚最大的一次跳跃**）

他的原话：「**我觉得主要是模型对这身衣服的构成看不清晰，所以描述很混乱，应该先分析这份服装是由哪些部分构成的，分开来分析，应该会清晰很多**」，随后又补了更狠的一问：「**这个角色在只穿内衣的情况下，要分步穿哪些部分才能穿起这套完整的造型？这是能分析的吧？**」

⇒ **平铺几十个问题 = 逼模型同时干两件事**（判断"这是什么" + 描述"它长什么样"），它两件都干不好，输出就乱。**换成「先分件 → 再逐件问 → 装配关系 → 穿衣序列」四步，质量立刻不同。**

| 步骤 | 干什么 | 实测 |
| --- | --- | --- |
| **S1 分件** | 这套服装由哪几件组成？从里到外 | 抓到了「围裙**翻领夹层内藏蓝色领带**」「束腰**上蓝下白**」这些平铺时**根本问不出来**的结构 |
| **S2 逐件** | 对每一件单独问：形状／颜色细节／边缘／装饰件／自身层数／材质 | 产出「竖条纹**约每 1.5cm** 一条；靠边双横纹**间距 0.3cm**；最外窄白滚边 **0.2cm**」这类**可核对的量化** |
| **S3 装配** | 谁压谁、有没有夹层 | 答出「束腰四金扣里**最上一颗被围裙上沿遮住**」「袖口白花边说明**内衬袖长略长于连衣裙袖**」 |
| **S4 穿衣序列** | 假设只穿内衣，分步怎么穿 | 5 步逻辑全对，每步都给了"换顺序会怎样" |

** S4 为什么是今晚最稳的一步**：**穿衣顺序有唯一解**（物理约束），模型没法糊弄 —— 而"这是什么"是开放的，它就容易乱编。

> 注意：注意： **但 S4 暴露了一个更危险的毛病：推理步骤会编数字。** 同一次运行里，S2/S3 之外它自己报出「围裙前片纽扣**共 4 颗**」「束腰**6 颗**铆钉左右各 3」，而用户当场确认的是**围裙 3 颗、束腰 4 颗（两排各两颗）**。⇒ **它在"推演一个合理的女仆装"，不是在"看这张图"。**
>
> ⇒  **必须分开用，不能混**：
> - **分件(S1)／装配(S3)／穿衣(S4) ＝ 只用来「定结构」**（有几件、谁压谁、怎么穿）；
> - **逐件细节(S2) ＝ 只用来「取属性」**（几颗扣子、什么花纹、多宽）；
> - **拿结构步骤去取数字，必错。**

> 注意： **分件本身不稳定**：同一张图三次跑分别分出 **7 / 6 / 5 件** ⇒ **分件结果必须人工扫一眼**（而穿衣序列的**逻辑**三轮一致，变的是明细）。

>  **另一条血泪歧义（他当场解开）**：模型报「围裙扣子」时，前一轮说"两排每排两颗"、后一轮说"沿中线垂直 3 颗"，看似变卦 —— **其实它说的是两个不同部位**：**围裙前中线 3 颗** ／ **束腰带 4 颗（两排各两颗）**。
> ⇒ **纪律：问扣子/装饰件必须指明「哪一件衣服上的」，否则模型答的可能是另一件，看起来就像它变卦。** 同理适用于任何"同一种东西在多处出现"的提问（花边、蝴蝶结、系带……）。

###  铁律零 · 模型的"推理输出"必须过常识审查，**而审查是人的活**（2026-10-02 20:3x，本工具当场被指出后写下的）

**事故经过**：`layered.py` 的 S4 穿衣序列给出

> 1. 白色纱裙内衬　2. 浅蓝格纹中层裙　3. 深蓝连衣裙主体　4. **蓝白束腰**　5. **白色围裙**

**两处荒谬**：① 把**一件连衣裙自己的三层裙摆**当成三件、排成"穿三次"；② 把**束腰排在围裙里面** —— 而**束腰的作用就是束住连衣裙和围裙、修饰身形，它必须在最外面**。用户原话：**「束腰肯定在围裙外面啊，围裙里面穿束腰的意义是什么？自己好好思考一下啊，你不是深度思考嘛？」**

注意： **本工具的失职**：**不但没驳回去，还在报告里夸它"5 步逻辑全对"** ✗ —— **本工具把自己一整天在说的「判断不能外包给模型」，亲手违背了一次。**

⇒ **纪律（写死）**：
1. **模型给"推理型输出"（顺序／因果／该不该）时，必须逐条问自己「这在现实里说得通吗」** —— 不管它写得多流畅、理由多齐。
2. **越是头头是道，越要审** —— 流畅性恰恰是它最容易骗过人的地方。
3. **不能靠 prompt 解决**：本工具把「束腰的作用是束住里面、所以必须在外面」写进 prompt 后，它立刻照做 是 —— **但那说明闸门是本工具加的，它自己不会过**。**下一个新种类的荒谬它照样会犯。**
4. **判据**：识别出来的"事实"（几件、什么颜色、几颗扣子）可以信，**它推出来的"该怎么穿/该在哪"一律先当嫌疑犯。**

>  **同一批修正里得到的好结果（可复用）**：把「**一件衣服内部的多层结构算一件**，不能拆成多件；物理上能单独穿的才算一件」写进分件 prompt 后，分件数从 **5~7 件**收敛到**准确的 3 件**（连衣裙／围裙／束腰），而且 S3 能正确说出「**无整件被夹住，但围裙翻领夹层里的领带属局部隐藏部件、非独立服装件**」—— 概念分得很清。

###  大件／配件 两分法（2026-10-02 20:3x · 用户提的，**当晚质量最高的一次**）

他的原话：「关于穿衣顺序和服装构成，**再分割成大件 + 配件**，会不会好一点？比如说这里的连衣裙、围裙、鞋袜就是"大件"，而**束腰、领带、发饰、手套这些属于配件**」。

**实测（同一张图，`layered.py` v2）**：
- **大件 4**：深蓝连衣裙／白色围裙／白花边袜／深蓝玛丽珍鞋
- **配件 6**：领带（夹在围裙翻领夹层）／束腰（系在两件大件之外）／头饰（女仆帽，戴于头顶）／裙摆蝴蝶结（缝在裙摆外层）…
- **大件顺序**：连衣裙 → 围裙 → 袜 → 鞋（理由对：「因玛丽珍鞋是包脚款式，**袜子必须在鞋前穿好**」）
- **配件时机**：领带「在围裙之后」／**束腰「在围裙之后」**（理由：系于连衣裙外、围裙外，压在两件大件之上）
- **扣子数也对上了**：束腰「**4 颗金扣呈 2×2**」

>  **为什么这一招治本（本工具想清楚了）**：**「配件」这个类别自带一条物理约束 —— 它必须回答「固定在谁身上」。**
> 束腰 `attached_to = 围裙` ⇒ 它只能在围裙之后装 —— **这个推理是从数据里长出来的，不用往 prompt 里硬塞常识**。
> ⇒ **上一版是硬塞一句常识（治标）；两分法是改数据结构，让错误无法表达（治本）。**
> **通用教训：与其反复叮嘱模型「要讲常识」，不如把问题的结构改成「不讲常识就答不出来」。**

>  **同批修正的另一条也有效**：把「**一件衣服内部的多层结构算一件**（问自己：它能单独穿在身上吗？不能，那就是结构）」写进分件 prompt 后，分件数从 5~7 件收敛到准确件数，且 S3 能正确区分「**无整件被夹住，但围裙翻领夹层里的领带属局部隐藏部件、非独立服装件**」。

###  对象 + 部位细节（嵌套结构，2026-10-02 21:0x · 用户提的第四层改进）

他的原话：「把大件+配件再分割成 **大件对象 + 部位细节**（比如纽扣这类）**+ 配件对象 + 配件细节**，细节与本体**一一对应**，可行吗？」

**做法**：细节**不再是平铺的第三个筐，而是嵌在每个对象内部**：

```json
{"main":[{"name":"连衣裙","covers":"...","color":"...",
          "details":[{"part":"前襟","desc":"..."},{"part":"袖口","desc":"..."}]}],
 "accessories":[{"name":"束腰","attached_to":"...","details":[...]}]}
```

⇒ **一一对应是结构保证的，不靠模型自觉** —— 这直接治了当晚反复出现的两个病：
① **扣子归属混乱**（围裙 3 颗 / 束腰 4 颗，一度被混成一处，看起来像模型变卦）；
② **细节被误当配件**。

**实测（图A，无先验）**：大件 4 ／ 配件 3，**连衣裙自带 8 项部位细节**，且**质量到了设计稿级别**：
> **前襟**：4 颗金色圆形金属纽扣（**直径约 1.5cm**），表面有**同心圆压纹**
> **腰封**：「**结构属连衣裙本体，非独立配件**」，宽 8cm，正面 **2 对金色铆钉、中心有凹陷十字纹**
> **裙摆**：三层（白棉荷叶边 4cm ／ 浅灰紫薄纱荷叶边 5cm ／ 深蓝…）
> **侧开衩**：自膝上 15cm 开衩，**衩口内衬白棉布、边缘浅金线锁边**

⇒ **腰封这次被结构自己放对了**（它一度是独立配件且排错位置）—— **又一次印证：改结构 > 塞规则。**

> 注意： **仍漏的一处**：它把角色头上的**鳍状耳**列成了配件「**耳饰——仿兽耳造型耳夹（无穿孔）**」，
> 而判据 4 明写"不是服装的东西不要列（尾巴／鳍等身体附属结构）"。
> ⇒ **"知道规则但不执行"是老毛病**：图B 那次它自己写下「纽扣误列——修正：移入 details」，**JSON 里却没动**。
> **结论：模型写下的"我知道错了"不能当已修正；这类自述要在报告里显式标出，交给人工裁。**

###  判据升级：从"字符集"到"实词覆盖 + 属性对立"（2026-10-03）

**起因**：拿真值集跑回归，**冲突 14/14 全红、确证 0 项** —— 报告完全失去分辨力。逐条追下去，发现三类错**全在判据自己身上**：

| 症状 | 真例（都是回归里实际出现的） | 修法 |
| --- | --- | --- |
| **全角/半角** | 模型答「四颗…呈 **2×2** 矩阵」、真值写「2x2」⇒ 明明全对，判错 | `norm_answer()`：NFKC 归一 ＋ `×`→`x` |
| **括号里的补充说明** | 「有宝石（位于领口正中）」vs 真值「有宝石」⇒ 括号内容把字符集撑大、Jaccard 掉到阈值下 | 归一化**同时保留"带括号"与"去括号"两个形态**，任一命中即算命中。注意： 有的关键信息**恰好只在括号里**（那条 `2×2` 就是）—— 只去括号反而丢信息 |
| **虚词被当成关键信息** | 真值「喷水的小鲸鱼」，模型答「有喷水孔…的小鲸鱼」，**只因少一个「的」字被判错** | `_STOPWORDS`：的/了/是/个/和/与/及/等… 不算关键信息。**但「有/无/不/各/两/上/下」不算虚词** —— 它们在是非题与数量题里就是答案本身 |
| **颜色对立被 Jaccard 抹平** | 「深蓝玛丽珍鞋（带扣为**银色**金属圆扣）」vs 真值「深蓝玛丽珍鞋，**金色**搭扣」⇒ 字符 Jaccard 高达 0.70，被判成 same | 新增 `_colors()` ＋ **颜色对立前置检查** |

**判据顺序（顺序本身就是判据的一部分）**：
**否定对立 → 颜色对立 → similar（归一化后） → 字符子集 → 实词全覆盖 → 冲突**

**颜色对立的判据是"各有一个对方没有的颜色"，不是"没有共同颜色"** —— 因为 `shoes` 那条两方共享「蓝」，共享色会把「银 vs 金」整个遮住。（早先就是写了"交集为空"才漏掉的。）

> 注意： **本工具自己在这上面栽的一个坑，值得单独记**：`_colors()` 里用 `c[-1]` 取颜色字，于是「金色」「银色」「白色」**统统归一到「色」**，把"金色 vs 银色"这种硬对立直接抹平。**单元测试 11 条当场逮住 2 条** —— 这就是为什么要**先写用例、再跑真图**，别拿真图当第一道闸门（真图的噪声会掩盖判据自身的 bug）。

**L3 复检改成"按部位裁切"**（原来只会把整图切上/中/下）：
- 问「领型」→ 先裁出**头面部那一条横带**再切三段；问「鞋」→ 裁下半身。
- 认不出部位才退回整图切三段。关键词表在 `eye.py` 的 `_ZONES`。
- **效果（同一批图、同一批模型）**：ref-a 冲突 **14 → 9**、确证 **0 → 5**；ref-b 冲突 **7 → 5**、确证 **1 → 3**。

>  **一条比判据更重要的发现：模型输出的随机性，大于判据差异。**
> 同一张图、同一套问题、隔 3 分钟跑两次，dashscope 的措辞就变了（一次写「呈 2×2 矩形布局」，一次写「两排各两颗，上下间距相等」）—— 分数因此浮动 1~2 项。
> ⇒ **单次分数不能当"能力"读**（无论涨跌）；看趋势就多跑几次取中位数，或只比"同一份答案在不同判据下的判定"。
> ⇒ **别把"这次分数掉了"当成"改坏了"** —— 本次两条看着像退化的项，逐条核对下来全是模型换了说法。

>  **严格下界的两条已知局限（不是 bug，别再修）**：
> ① 语义相同但字面全异的表述判不出来 —— 真值「2x2」vs 答案「两排各两颗」、真值「发根深发梢浅」vs 答案「从深蓝渐变到浅蓝」，**这两条永远会判错**；
> ② 想覆盖这类情况只能用 LLM 裁判（`vscore.py`，宽松上界）。**真实水平在严格与宽松之间**，两个数一起看。

###  复检为什么"越查越糊"：四个真 bug（2026-10-03 实测 · 他发的一张 8 MP 立绘逼出来的）

**现象**：2346×3411 的立绘，复检六个块里**五块答「看不清」**，剩下那块同一模型还给出互相矛盾的形状（黑桃／梅花）。

| 问题 | 真因 | 修法 |
| --- | --- | --- |
| **"放大复检"从来没真放大过** | `_ask_regions` 的缩放按**宽度**算（`int(1600/宽)`），而横带保留整幅宽 2346px ⇒ 永远算得 1.0 | 改成**按长边**算、允许放大：`min(3.0, 2000/长边)`；目标 2000 与 `img_b64` 的 max_side 对齐，送进去不会再被缩 |
| **裁切形状错** | 裁的是"整幅宽的一条横带"，而立绘里人物只占中间一条 ⇒ 送进模型后**人反而更小** | 改裁**以人物中轴为中心的正方形框**：1534×1534 → ×1.30 → 2000×2000 |
| **轮 2 切错方向** | 正方形框**横着切三条**（1534×511）—— 宽度一点没减、只放大 1.3× | 改切 **2×2 象限**：843×843 → ×2.37 → 2000×2000，水平方向也聚焦 |

**第四个、也是最阴的一个**：`is_noclue()` 原来只做**子串匹配**。
dashscope 答「右手抬起，五指微张，指尖朝前，呈轻盈抓取或施法状；左手未完全显示，**无法**判断具体姿态」—— 主体答得好好的，**只因为结尾补了一句"无法判断"**，整条被判成"没看清"。
**连锁后果**：`_real()` 滤掉它 → `info()` 归零 → **轮 2 复检压根不触发**；L2 的分歧检测也会把这条当成"该模型没答"。
⇒ 判据改成：**短回答看词**（≤20 字含这些词＝真没看清），**长回答看这些词是不是主体**（剥掉命中词后剩不足 12 字才算）。单测 8/8。

> 注意： **但"效果"这次没法用分数证明**：同一张图连跑四次，**每次 L2 挑出的冲突项都不一样**（模型措辞每次都变），复检结果自然对不上号。
> 稳定能观察到的只有**耗时**：167s → 97~126s（复检块从 6 降到 2~4）。
> ⇒ 又一次印证那条通则：**模型随机性 > 改动差异**。机制层的对错（框裁多大、放大几倍、轮 2 触发没有）**是可验证的**；"变好了没"得靠多次取中位数。

| --- | --- |
| **百炼 `qwen3-vl-plus`** | **主力**。0.6~17s，答得最细（同一张 8 MP 立绘能给 800~1070 字的结构化描述），**默认必上** |
| **本地 `ollama qwen2.5vl:7b`** | **第二意见**。1~9s、无限次不烧额度；答得短、常漏细节，但**快且不要钱** ⇒ 适合并排与批量筛图 |

###  模型复读必须折叠 —— 否则它会被当成"观察结果"（2026-10-03 · 用户当场抓出来的）

**现象**：ollama 在一张 8 MP 立绘上把「角色的腿部有红色的蝴蝶结装饰。」连着吐了 **24 遍**。

**真正的问题不在模型**（小模型复读是常见故障），**在流水线**：
- 那 24 遍**原样进了报告的"原始回答"**；
- L2 的分歧检测还把它归成了一个条目 ——「重复蝴蝶结列举（共 29 次）」，**列在孤证项里**。

⇒ **复读不是描述，是故障。** 最坏的地方不是难看，是让"多模型交叉"里凭空多出一个谁都没看见的观察项 —— **等于往证据链里掺假**。

**修法**（`eyeprobe.collapse_repeats()`，在 `call()` 里对所有后端生效）：
- 判据：同一行（**剥掉行首编号/项目符号**后）重复 ≥4 次，且占非空行 ≥35%；
- 处理：只保留前 2 次，其余丢掉，末尾追加 `[!] 模型复读：…重复了 N 次，已折叠`；
- 控制台同时打 `[!] 复读 xN 已折叠`，`usage.repeat_collapsed` 带次数（上层可判）。

**实测**：拿报告里那段**真实文本**跑 → 1110 字 → 633 字、检出 24 次 是；带编号的复读同样检出 是；正常回答与短回答 **0 误伤** 是。

> 注意： **本工具第一版漏掉的情况，比 bug 本身更值得记**：单测时本工具给复读行**加了编号**（`10.` `11.` …），于是每行都"不一样"、检测直接失效 —— 差点得出"逻辑没问题"的假绿结论。
> ⇒ **测试数据必须用现场原文，不能自己"整理"一遍再测。**

### 复检是**两轮自适应**的（2026-10-02 晚）

轮 1：整图切三段、放大、逐块重问 ＋ 每块取主色（算法证据）。
轮 2：**若没收敛，自动挑"给出实质答案且最长"的那一段，再切三份**（等于放大到 9 倍）重问。

> 注意： **收敛判定踩过三次坑，都写死了**：
> ① 早期是"某块内答案去重后剩一个" ⇒ 过滤掉失败项后**一个孤零零的「看不清」被当成一致**，把分歧项**错误升格成确证**。
> ② 改成精确相等后又太严 ⇒ 「右侧」vs「右」本来是同一答案，却被判成不收敛。
> ③ 加了"一详一略算兼容"之后**顺序又错**：`similar()` 排在否定检查前面，而「露肩」是「不露肩」的**子串** ⇒ containment 先命中，**把语义相反的两个答案判成"一致"**。
> **现判据（`relation()` 三分类）**：**先查否定**（一方有一方没有 ⇒ 直接 conflict）→ 再判 similar（same）→ 再判字符子集（compatible）→ 否则 conflict。
> **通用教训：判据自己的错是"静默地把不确定说成确定"，比模型幻觉更危险** —— 没人会去质疑一条标着"确证"的结论。

###  用户当场纠正后的第二条铁律：**问法能修"用词"，修不了"看错"**（2026-10-02 19:2x）

他逐条纠正了那次的输出：**「兽耳」其实是头鳍** ／ **「立领」其实是翻领** ／ **左右手反了**（脸朝镜头，左右要换算）／ **不露肩**。

据此改了 `build_schema_prompt`（加两条硬要求：**左右必须写参照系**、**非人特征不许拿常见动物部位顶替**），重跑同一张图：

| 症状 | 加提示后 | 结论 |
| --- | --- | --- |
| 「兽耳状结构」 | → **「鳍状耳（耳尖分叉呈鳍形）和鲸鱼尾鳍状尾巴」** | 是 **词汇表问题，提示可解** —— 还顺带多读出了鲸尾 |
| 左右手 | 写明了「角色左手（画面右侧）」，**但判断仍反** | 否 提示只让它"交代参照系"，没让它"判断对" |
| 立领 vs 翻领 | 照错不误 | 否 **形状判断错误，提示无解** |

⇒ **写法层面的错（用词、参照系缺失）可以靠 prompt 修；判断层面的错（形状认错、左右判断反）只能靠更强的模型、放大复检、或人眼。别指望调 prompt 把"看错"变成"看对"。**

> 注意： **另一条配套纪律**：**这类"人眼一眼"的事（肩有没有露、左右手拿什么），复检两轮看不清就该早问用户，不要死磕额度**。用户是判定者，一句话比三次复检值钱。

> 注意： **`eye.py` 自己踩过的两个坑（都已修，写下来是因为它们很典型）**：
> ① **统计口径错**：把"复检过的项"直接算成"存疑"，而按判据复检**收敛**的应算确证。
> ② **收敛判定错（更严重）**：早期的 `converged` 只是"某一块内答案去重后剩一个"—— 于是把失败项过滤掉之后，**一个孤零零的「看不清」被当成了"一致"**，把分歧项**错误升格成确证**。现在的判据写死：**同一块内至少 2 个模型作答、答案相同、且都不含"看不清/无法/不能确定"** 才算收敛。
> ⇒ **通用教训：判据本身也会错，而且它的错是"静默地把不确定说成确定"** —— 比模型幻觉更危险，因为没人会去质疑一个标着"确证"的结论。

## 铁律一 · 能算的绝不问模型

| 要什么 | 用什么 | 不许用什么 |
| --- | --- | --- |
| 尺寸 / 比例 / 像素位置 | PIL 读图、`vision_crop` 坐标 | 模型目测（实测：头身比被读成 5，实际 7） |
| 颜色 | PIL 量化取色、`vision_colors` | 模型描述（实测：两模型对同一区域说"白"和"黑"） |
| 印刷体文字 | tesseract（本地） | 云端模型（浪费额度且更慢） |
| 两图差异 | `vision_pixel_diff` | 模型比对（会漏） |

**判据**：这个问题**能用算法回答**吗？能 → 不许用模型。

## 铁律二 · 看细节必须放大

- 目标**小于全图 5%**（扣子 / 花纹 / 小字 / 饰件）→ **先裁出来放大再问**
- 精细问题（颜色 / 计数 / 朝向 / 有没有）→ 整图问 = **等于没问**
- 裁图坐标优先用 `vision_ground`（专业定位），**不要信模型自报的 bbox**
  - 实测事故：模型把"领口扣子"定位到 `y=213`（脸），真实位置是 `y=501`

## 铁律三 · 结论要交叉，而且"一致"不等于"正确"

- 写进档案 / 交付的结论 → **至少两个独立来源**（两模型，或 模型 + 算法证据）
- 模型之间打架 → **不许挑一个信**，标"未定"并去验
- 注意： **模型一致 ≠ 正确**：实测两个模型**异口同声**说衬衫扣是金色，算法取色显示是**深蓝近黑**（`#272948` 占 62%）
- 模型给出的"依据像素坐标"**可能是编的**（实测：它说依据 x=200–300，而裁剪块总宽 260）

## 铁律四 · 不确证就标注

- 任何外观 / 细节结论 → 带 **确证 / 推断 / 存疑** 三档标记
- 模型说"看不清"时 → **不许替它补一个合理答案**（实测事故：把"看不见袜口"写成"短袜"）

## 分工表：什么时候用哪一层

| 任务 | 用哪层 | 理由 / 实测 |
| --- | --- | --- |
| 印刷体文字 | **L0 tesseract** | 本地、0 成本；`engine=tesseract` 已接进插件 |
| 艺术字 / 海报字 | **L1 百炼** | tesseract 对风格化字体**一个字都读不出**，VLM 读得准 |
| 场景 / 构图 / "这是什么" | **L1 百炼** | 0.6~1.1s，最快 |
| 精细外观 / 颜色 / 计数 | **L0 取色 + L3 复检** | 模型这块最不可靠 |
| 批量筛图（几十上百张） | **L2 Ollama** | 本地无限次、不烧额度 |
| 交叉验证 / 角色建档 | **L3 eyeprobe + vscore** | 并排 + 打分 |
| 断网 / 额度耗尽 | **L2 Ollama → L1 智谱** | 兜底 |

**延迟参照**：百炼 `qwen3-vl-plus` 0.6~9s ｜ 智谱 `glm-4.6v-flash` 2~17s ｜ OVH 匿名常 429 ｜ 本地 Ollama 未测。

**额度参照**：百炼新用户每系列 100 万 token（约 0.0006 元/张）｜ 智谱免费但**高峰期会 429**（实测两次）｜ OVH 匿名 2 次/分钟。

## 工具箱（本目录）

| 脚本 | 干什么 | 何时用 |
| --- | --- | --- |
| **`eye.py`** | **一条命令走完全流程**（L0 算法 → L1 多模型 → L2 分歧 → L3 自动复检 → L4 分级报告），带全局时间预算 | **默认入口** —— 要看图先跑它 |
| `layered.py` | 分层解析：S1 分件 → S2 逐件 → S3 装配 → S4 穿衣序列（大件／配件两分法 + 部位细节嵌套） | 服装结构 / 构成混乱时 |

## 附：真值表自身的纪律

真值也会错。**当两个独立模型同时反对一条真值，先怀疑真值**。
- 实测：`brooch` 那条原本写"有独立胸针"，复检后改成"领结中央嵌深蓝宝石（属领结一部分）"
- 实测：`shirt_button_color` 原写"深蓝"、模型都说"金色"，算法取色证明**真值对、模型错** —— 所以**不能一律怀疑真值，要有独立证据**
