# 无窗口启动器被编译为控制台子系统，导致周期性弹窗并抢占焦点

## 问题

任务计划每次触发时，主显示器上闪出一个黑色控制台窗口（存活约 59 ms），并抢占前台焦点，打断鼠标操作。与输入完全无关地周期性出现，容易被误判为显示链路故障。

**症状指纹**（用于快速识别同类故障）：

| 指纹 | 观测值 |
| --- | --- |
| 可见窗口类名 | `ConsoleWindowClass` |
| 窗口进程 | 声称「隐藏窗口」的启动器可执行文件**本身**，而非其子进程 |
| 窗口存活时长 | 数十毫秒（不足以看清标题） |
| 触发周期 | 与任务计划的重复间隔一致 |
| 伴随影响 | 前台焦点被抢占，输入与鼠标操作被打断 |
| 任务侧指标 | 任务返回码 0、日志正常写入 —— **任务侧指标完全正常，不能作为排除依据** |

三条特征（周期性 / 窗口存活极短 / 抢占前台焦点）已足以指向「有进程周期性弹窗并抢焦点」，无需再考虑显示链路。

## 原因

可执行文件的 PE 子系统类型与其宣称的行为不符。机制链：

1. 旧版启动器的 PE 头为 `Subsystem = 3 (Console)`。
2. 任务计划由 `svchost` 拉起，而 `svchost` 本身没有控制台。
3. Windows 对「控制台子系统程序 ＋ 父进程无控制台」的组合，会为该进程**自身**分配一个新的控制台窗口。
4. 源码中的 `CREATE_NO_WINDOW` 只传递给**它创建的子进程**，管不到它自己。

⇒ **「隐藏窗口」必须连同自身一起隐藏。**父进程自身的 PE 子系统决定了它会不会被分配控制台；要得到真正无窗口的启动器，必须编译为 GUI 子系统。PE 头实测对照：旧产物 `Subsystem = 3 (Console)`，新产物 `Subsystem = 2 (GUI)`。

## 方法

修复：以 GUI 子系统重新编译（`/target:winexe`）。GUI 子系统进程不分配控制台，窗口无从产生；其子进程仍由 `CREATE_NO_WINDOW` 保证无窗口。

```powershell
csc.exe /nologo /target:winexe /optimize+ /out:<home>\run-hidden.exe <home>\run-hidden.cs
```

### 取证方法

自制探测器抓取现场（枚举**可见顶层窗口** ＋ 订阅进程启动跟踪 ＋ 高频轮询 ＋ 按窗口坐标判定屏幕归属）。关键取证在于**两条独立证据链的时间对齐**：探测器捕获的窗口出现时刻与任务计划的最后运行时刻（返回码 0）精确吻合，从而把窗口归属到该任务，排除其他周期性进程。窗口枚举不能只监视前台窗口，否则会漏掉「已弹出但未抢到焦点」的窗口。现场捕获记录见 [`raw/invisible-console-window-capture.md`](raw/invisible-console-window-capture.md)。

### 验证（生产条件下 A/B）

| 版本 | 进程树 | 屏幕表现 |
| --- | --- | --- |
| 旧版（Console） | 启动器 ← `svchost` | 弹出 `ConsoleWindowClass` 窗口并抢占焦点 |
| 新版（GUI） | 启动器 ← `svchost` → `powershell.exe` → `conhost` | **零窗口、零抢焦点** |

功能未回归的回读证据：看门狗任务实跑返回码 0、日志正常写入；另建一次性任务实测「启动器 → `cmd.exe /c md <目录>`」，目录成功创建。任务的 State / RunLevel / UserId 在改动前后一致。

### 改动台账（全部可回滚）

| # | 改动 | 回滚点 |
| --- | --- | --- |
| 1 | 启动器重新编译为 GUI 子系统 | `backups\run-hidden-<stamp>\run-hidden.exe.bak` |

| 5 | 启用「任务计划」操作日志 | `wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:false` |

## 结果

窗口与焦点抢占完全消失，任务功能未回归。启动器回退则故障必然复现（回退仅用于对照实验）；任务配置与取证开关按上表回滚。

### 可迁移结论

1. **「隐藏窗口」必须覆盖自身。** `CREATE_NO_WINDOW` 只作用于子进程；父进程自身的 PE 子系统决定了它是否会被分配控制台。
2. **验收判据必须是「屏幕上有没有东西」，不能是「任务返回码为 0」。**本次缺陷上线时只验证了返回码与心跳，因而潜伏了数小时。**脚本自行打印的成功信息不构成证据。**
3. **复现必须还原真实条件。**从**有控制台**的父进程（交互式 shell）启动时，子进程继承控制台、**不会新建窗口** —— 测试环境正好把缺陷隐藏起来；只有由任务计划（无控制台的父进程）拉起才能复现。
4. **偶发弹窗的通用抓法**：枚举可见顶层窗口 ＋ 订阅进程启动跟踪 ＋ 高频轮询 ＋ 按窗口坐标判定屏幕归属。
5. **不得以 `.bak` 后缀命名可执行文件的备份。**此类文件被双击或经 ShellExecute 调用时会弹出「选取应用」对话框（实测发生，且弹窗会残留，需手动终止 `OpenWith.exe`）。

### 已知限制

- **遗留隐患**：启动游戏所触发的辅助工具拉起路径尚未包裹，启动游戏时会弹出一个控制台窗口（包裹后仅隐藏其控制台，图形界面不受影响）。是否需要处理待定。
- **悬案（原因未查明，不编造解释）**：在 shell 中用 `&` 直接调用 GUI 子系统可执行文件时功能测试不通过（退出码为空、子进程无输出）；而生产路径（由任务计划拉起）实测正常。两者差异的原因未查明。
- 本次仅验证了「窗口是否出现」与「任务功能是否正常」，未对旧版在其他宿主环境（如带控制台的交互式调用）下的行为做穷尽枚举。
