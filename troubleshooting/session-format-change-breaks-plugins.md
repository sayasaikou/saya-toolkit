# 宿主会话格式变更导致全部插件加载失败

## 问题

宿主应用升级后，插件层整体加载失败：界面报「插件加载失败」，宿主本体与服务正常，卸载重装插件无效，冷启动必现。

本故障的核心特征是不对称：**所有静态检查均通过**（配置文件合法、插件文件齐备、加载清单无缺失、界面显示已启用），只有运行期解析失败。因此「检查文件是否存在」一类手段永远无法定位此类故障。

整体性失败是识别此类故障的首要判据：多个互不相关的插件同时失效 ⇒ 不是某个插件的问题，而是共享的上游契约发生变化。

## 原因

宿主侧会话记录结构发生版本变更（字段嵌套层次变深）。插件侧按旧结构解析，假设目标字段直接位于顶层对象；新结构下该字段位于嵌套位置或不存在，取值得到 `undefined`，对其取属性即抛异常。

异常发生在插件初始化的早期阶段。多数插件宿主在加载期遇到未捕获异常时会放弃整个插件层，而不是仅跳过出错的插件。这是「单个插件解析失败 → 全部插件不工作」的放大路径。

### 会给出误导性结论的检查

| 检查手段 | 结果 | 为何不可信 |
| --- | --- | --- |
| 插件文件是否存在 | 全部存在 | 文件存在与解析成功无关 |
| 配置文件语法 | 正确 | 故障点在数据解析，不在配置 |
| 加载清单 / boot manifest | 无缺失 | 清单反映「声明要加载什么」，不反映「什么加载成功了」 |
| 重新安装插件 | 无效 | 同一份代码配同一种新数据，必然同样失败 |
| 「插件已启用」界面提示 | 显示正常 | 声明层面的状态，不是运行期状态 |

唯一有效的信号是运行期异常栈。

## 方法

修复方向：**读取侧写双形态兼容**，而不是把数据改回旧格式（改数据等于放弃升级，兼容读取是一次性成本）。

1. 解析前先探测结构形态（判断关键字段位于哪一层），再走对应分支。
2. 对缺失字段给默认值，保证任何一条历史记录都不会让整批解析失败。
3. 用两套形态的数据各跑一次测试。

### 验证清单（顺序即优先级）

| # | 验证项 | 判据 |
| --- | --- | --- |
| 1 | 冷启动（非热重载） | 插件层恢复，无加载失败提示 |
| 2 | 插件脚印文件 | 时间戳推进 —— 证明插件真的执行过，而非只是被声明 |
| 3 | 新旧两套数据各跑一次 | 均通过 |
| 4 | 加载清单 | 仍无缺失（回归确认） |

## 结果

冷启动后插件层恢复，注入类插件脚印文件时间戳推进，新旧两套数据均可解析。

### 回滚

- 回滚宿主版本需保留升级前的安装包与用户数据目录。注意：**新格式的会话数据可能无法被旧版本读取**，回滚宿主不等于回滚数据。
- 临时旁路：停用读取会话数据的插件，牺牲功能换可用性。
- 本类故障的最佳回滚点是升级前对用户数据目录做完整快照 —— 跨版本格式变更事后补备份来不及。

### 可迁移结论

1. **「文件都在」不是证据。** 静态完整性检查只能排除一类故障，运行期契约变更不在其覆盖范围内。判断组件是否真的工作，要找它主动留下的痕迹，而不是找它应该存在的文件。
2. **全部一起坏 ⇒ 查上游契约，不要逐个修下游。**
3. **插件宿主应当隔离加载失败。** 一个插件初始化失败即拖垮整层，是把小故障放大成大故障的设计；若宿主不提供隔离，插件侧需保证初始化路径不抛异常（把可能失败的逻辑推迟到首次实际使用）。
4. **对不属于自己的数据结构保持宽容。** 字段可能不存在、可能换层、可能是历史遗留形态。
5. **升级大版本前先快照用户数据。**

### 已知限制

1. 本文描述失败机制与排查路径，不针对特定宿主的特定版本；任何「插件读宿主私有格式」的架构都可能复现同类事故。
2. 兼容读取有长期成本：每支持一种历史形态即多一条分支。确认旧形态数据已不存在时，应显式移除兼容分支并记录移除依据。
3. 不同插件宿主对加载期异常的处理策略不同（整层放弃或仅跳过出错项）。本故障中表现为整层失败，换一个宿主可能仅部分功能失效 —— 症状会变，但根因判据（整体性 vs 单点）依然适用。
4. 未做跨版本矩阵测试（多宿主版本 × 多数据形态），只验证了两种形态的端点。
