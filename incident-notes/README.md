# incident-notes：故障记录

本目录收录生产环境中实际发生的故障。每份文档固定四节：**问题 → 原因 → 方法 → 结果**。

## 为什么是四节

这四节对应排查者实际需要的四件事：这是什么故障（能不能对上号）、为什么会这样（能不能理解机制）、当时怎么处理与验证的（能不能照做）、最后成了什么样（能不能直接迁移结论）。按这个顺序读一遍，就能判断「是否同一类问题、下一步做什么」。

## 编写规范

1. **不写叙事。** 正文不出现具体日期、对话、人名或角色描述。原始材料（事件序列、对话片段、逐条证据原文）归 `raw/`，正文只引用其结论。
2. **不写个案细节，只写可复用判据。** 正文里出现的任何一句话，应当能直接搬进另一个项目的同类故障记录。
3. **结论分级。** 已实测确证、推断、未验证三种状态分开标注；不得把推断写成已验证事实（这是这类文档最容易失去信任的地方）。
4. **量化数据必须来自日志或命令输出**，不来自回忆；无法复核的数字不写。
5. **失败的尝试同样要写**，包括尝试内容与失败原因，否则后人会重走一遍。
6. **回滚方案要具体到文件与步骤**，而不是「恢复备份」这种结论。

## 四节各自写什么

| 节 | 内容 | 体量参考 |
| --- | --- | --- |
| `## 问题` | 可观测现象、影响面、**识别判据**（尤其是会给出误导性结论的检查） | 1–3 段 |
| `## 原因` | 机制层面的原因，含故障被放大的路径 | 1–3 段 |
| `## 方法` | 修复方向与为何选它、验证清单（顺序即优先级） | 1–2 段 ＋ 表格 |
| `## 结果` | 修复后的实际状态、回滚方案、可迁移结论、已知限制 | 分段 ＋ 列表 |

## raw/

`raw/` 保存不适合放进正文的原始材料：带时间戳的事件序列、原始描述、逐条命令输出与环境记录。正文只写结论，具体材料放这里备查。新增文档时不必强行拆分 —— 只有当正文里出现「叙事」时才把那段搬到 `raw/`。
