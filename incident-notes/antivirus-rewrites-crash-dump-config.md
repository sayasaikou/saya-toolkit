# 事故复盘：反作弊软件反复改写系统转储配置

> 事故编号：INC-2026-0925-04 ｜ 首次观测：2026-09-21 ｜ 累计改写：**34 次** ｜ 状态：**根因已定案，现场抓获待补**
> 影响面：蓝屏内存转储的**取证链路** —— 配置被改写期间发生的蓝屏，转储不会落在运维方指定的目录里
> 关联：本事故与 [bsod-triage.md](bsod-triage.md) 的蓝屏排查**直接相关** —— 后者依赖转储文件定案，而本事故会让转储「消失」

> **证据分级约定**：本文所有结论标注为「实测」「推断（非确证）」或「待确认」三档，三档不混写。
> **路径约定**：`<DUMP_DIR>` 指代部署时配置的转储目录（按实际部署替换，本文不写具体路径）。

---

## 1. 摘要

运维方为蓝屏取证配置了「完整内存转储 → `<DUMP_DIR>`」。此后一个每 30 分钟执行一次的守卫脚本持续报告：

```
REVERTED(CrashDumpEnabled,MinidumpDir) -> re-applying
```

即：有两个注册表值被反复改回 Windows 默认——`CrashDumpEnabled` 被改成 `3`（小内存转储）、`MinidumpDir` 被改成 `%SystemRoot%\Minidump`。守卫脚本每次把它焊回原值，随后又被改回去。**累计实测 34 次。**

**直接后果**：如果蓝屏恰好发生在这段「被改写」的窗口内，转储会落在 `C:\Windows\Minidump\`，而运维方按配置去 `<DUMP_DIR>` 找 —— **找不到**。

**根因（三条独立证据交叉，指向一致）**：带**内核级反作弊**的游戏运行时，其反作弊模块会主动改写这两个值。二进制字符串、值指纹、时间窗三方面证据同时命中同一族模块。

**处置**：① 保留守卫脚本（把配置焊回原值，降低窗口占比）；② 在 `CrashControl` 键上开启注册表审核，抓取改写者的**进程名与 pid** —— 把「推断」变成「现场抓获」。

**未完成项（明确的结案判据）**：尚未抓到一次带进程名的改写事件。**抓到一条 `4663` 事件、其中含 `ProcessName`，本事故方可结案**（见第 9 节）。

---

## 2. 现象与症状指纹

**现象**：蓝屏后按配置去 `<DUMP_DIR>` 找转储文件 —— 目录是空的 / 缺最近一次崩溃的转储。

**中间现象**：配置守卫脚本的日志里反复出现 `REVERTED(...) -> re-applying`，自愈后又会被改回去。

**症状指纹**（用于识别同类问题）：

| 指纹 | 说明 |
| --- | --- |
| **只有特定的两个值被动** | `CrashDumpEnabled` 与 `MinidumpDir`。同键下的 `AutoReboot` / `DumpFile` / `LogEvent` / `Overwrite` / `DumpLogLevel` / `EnableLogFile` **一个都没动** |
| **改回的方向永远是 Windows 默认** | `CrashDumpEnabled=3`（小转储）＋ `MinidumpDir=%SystemRoot%\Minidump` |
| **守卫一焊回、过一会儿又被改** | 呈周期性拉锯，而不是一次性事件 |
| **改写集中出现在「游戏运行时段」** | 游戏一退出，改写立即停止（见第 5.3 节） |
| ⚠️ 误导性健康检查 | 守卫脚本自身每次都会「修复成功」，日志看起来在正常工作 —— **它只证明配置被改过，不证明配置稳定** |

**为什么这个指纹重要**：它把问题从「系统故障」重新归类为「第三方软件的**设计行为**」—— 后者不能靠修系统解决，只能靠规避与取证。

## 4. 根因

**根因（实测 + 推断组合，见第 5 节证据链）**：某带**内核级反作弊**的游戏（本例为腾讯 AntiCheatExpert / ACE 系）在运行时会**主动改写** `CrashControl` 下的转储配置，把它改回「小转储 + 系统默认目录」。

**为什么反作弊要动这个**：反作弊自身需要在内核态抓取崩溃现场（转储模块里可见 `MiniDumpWriteDump` 与 `Q?MiniDumpType:%d;` 之类的字符串）。把系统配置固定到它自己期望的形态，是它的**设计行为**，不是故障。

**为什么它要改 `MinidumpDir`**：小转储的默认落点是 `%SystemRoot%\Minidump`；把目录指回默认值，可以保证它自己的转储收集路径可预期。

**关键限定（不要越界引用）**：

- 本事故**不是**「系统被破坏」，也**不是**「配置丢失」—— 配置每次都被守卫完整写回；
- 本事故**不影响**游戏运行，也**不建议**为了转储去对抗反作弊（见第 8.4 节）。

## 5. 证据链

### 5.1 证据一：值指纹（只有这两个值被动）

回退现场的注册表快照（`backups\crashconfig-<时间戳>\crashcontrol-before.reg`）：

```
"AutoReboot"       =dword:00000000   ← 未动（运维方设定值）
"CrashDumpEnabled" =dword:00000003   ← 被改成「小内存转储」
"DumpFile"         =hex(2): <DUMP_DIR>\MEMORY.DMP   ← 未动
"MinidumpDir"      =hex(2): %SystemRoot%\Minidump   ← 被改成默认令牌
"LogEvent" / "Overwrite" / "DumpLogLevel" / "EnableLogFile"  ← 未动
```

⇒ 改写者**只要这两个值**，且要的是「小转储落在系统默认位置」。这排除了「注册表整体被回滚」「配置文件损坏」等假设。

### 5.2 证据二：二进制字符串（直接命中）

对反作弊模块文件做字符串扫描，同一文件内**同时存在**下列串：

```
CrashControl
CrashDumpEnabled
MinidumpDir
%SystemRoot%\Minidump
%SystemRoot%\MEMORY.DMP
MiniDumpWriteDump / Q?MiniDumpType:%d;
```

- 主体文件：反作弊模块目录下的 `ACE-Trace.dll`（v7.6.2212.89，**2,377,608 字节**，签名有效）；
- 同族文件：`<Steam库>\steamapps\common\<游戏>\Launcher\tenprotect\BugTrace.dll`（TenProtect，腾讯的另一套反作弊）**命中同样的三个串**。

⇒ 这两套模块**有能力**写这两个值，且代码里明确写死了「默认目录」这个字符串。

### 5.3 证据三：时间窗吻合

- 全部 34 次回退**都落在该游戏的运行时段**；
- 09-25 那 14 次集中在 **10:55–17:25**（守卫每半小时巡检一次，因此观测频率被巡检周期限制）；
- **操作者一退出游戏，改写立刻停止** —— 18:25 / 18:55 / 18:57 三次巡检都是 `OK`。

### 5.4 附带发现：三份此前「消失」的转储

排查过程中检查了 `C:\Windows\Minidump\`，发现三份转储，其中 **一份此前从未出现在 `<DUMP_DIR>`**：

| 文件 | 时间 | 大小 | 说明 |
| --- | --- | --- | --- |
| `092126-15718-01.dmp` | 09-21 18:06 | 6.39 MB | — |
| `092126-15906-01.dmp` | 09-21 18:42 | 6.51 MB | — |
| **`092226-15843-01.dmp`** | **09-22 08:30** | **5.35 MB** | **正是当天 08:28 那次蓝屏留下的转储**，因配置已在游戏时段被改写而落到了默认目录 |

三份已**逐哈希校验**后拷入 `<DUMP_DIR>` 归档。

> **这条证据的价值**：它把「配置被改写」从一个理论风险，变成了一次**已经造成实际取证缺口**的事件。

### 5.5 现场抓获的取证装置（已就位，尚未触发）

对 `HKLM\SYSTEM\CurrentControlSet\Control\CrashControl` 启用注册表审核：

1. 对该键设置 **SACL**（`Everyone` / 成功）；
2. 打开 **对象访问 → 注册表** 子类审核（`auditpol`）；
3. 守卫脚本每次巡检时附带调用取证脚本，一旦检测到改写，就从安全日志里捞出对应事件并**解析出进程名 + pid + 时间**。

**两个实测坑（务必注意，否则一条都抓不到）**：

| 坑 | 说明 |
| --- | --- |
| 事件 ID 是 **`4663`** 而不是 `4657` | 该键上的写操作记成「对象访问」`4663`；只有**值真的变了**才会补一条 `4657`。**同值重写只记 `4663`** —— 按 `4657` 过滤会漏掉绝大多数 |
| `ObjectName` 是 **`\REGISTRY\MACHINE\SYSTEM\ControlSet001\Control\CrashControl`** | **不是** `CurrentControlSet` 那个写法。按 `CurrentControlSet` 匹配会**一条都抓不到** |

**安装前状态已存档**（原为 `No Auditing`），可完整回滚（见第 7 节）。

## 6. 修复措施与验证

### 6.1 已执行的处置

| # | 措施 | 状态 |
| --- | --- | --- |
| 1 | 保留配置守卫脚本：**开机触发 + 每 30 分钟巡检**，检测到改写即焊回原值并写日志 | 运行中 |
| 2 | 补捞 `C:\Windows\Minidump\` 里的历史转储，逐哈希校验后归档到 `<DUMP_DIR>` | 已完成 |
| 3 | 在 `CrashControl` 上开启注册表审核（SACL + 对象访问子类） | 已安装 |
| 4 | 取证脚本接入守卫巡检，附带解析 `4663` 事件中的进程名 | 已就位，等待触发 |
| 5 | 把「蓝屏排查必须同时检查两个转储目录」写入排查规程 | 已落地 |

### 6.2 验证方式与判据

- **配置侧**：守卫日志不再出现 `REVERTED` ⇒ 改写停止（**只有游戏不运行时才成立**，见限制）；
- **取证侧（结案判据）**：抓到**至少一条** `4663` 事件，且事件中能解析出**改写进程的进程名** ⇒ 本事故结案，可把「推断」升级为「实测」；
- **有效性判据**：下次游戏时段内发生蓝屏时，**两个目录都要查**：

```powershell
Get-ChildItem -Path '<DUMP_DIR>', "$env:SystemRoot\Minidump" -Filter *.dmp |
    Sort-Object LastWriteTime -Descending | Select-Object -First 10 FullName, Length, LastWriteTime
```

### 6.3 关于「要不要根除」的结论

**不要试图根除。** 反作弊改写这两个值是它的设计行为；与它对抗（拦截其写入、禁用其服务、修改反作弊模块）存在**账号风险**，且不属于运维方可以单方面处置的范围。

**接受的现实**：靠守卫把「配置错误的窗口」压缩到最小，接受**游戏时段内发生的蓝屏可能只有小转储**这一代价。

## 7. 回滚方案

| 项 | 回滚方式 |
| --- | --- |
| 配置守卫脚本 | 停止并注销其计划任务（`Unregister-ScheduledTask`）；注册表值不会自动改回，需手工设置 |
| `CrashDumpEnabled` 恢复原值 | `Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CrashControl' -Name CrashDumpEnabled -Value 3 -Type DWord` |
| `MinidumpDir` 恢复默认 | `Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CrashControl' -Name MinidumpDir -Value '%SystemRoot%\Minidump' -Type ExpandString` |
| 注册表审核 | 见 `backups\crashctl-audit\before-auditpol.txt`（原为 `No Auditing`）与 `before-sacl.txt`（原 SACL 为空）；按存档还原或直接移除该键的 SACL |
| 归档进 `<DUMP_DIR>` 的转储 | 原文件仍在 `C:\Windows\Minidump\`，是**拷贝**而非移动，可直接删除归档副本 |

⚠️ **回滚审核前先确认**：移除 SACL 后，安全日志里已有的 `4663` 记录**不会被删除**，但**新的改写事件将不再被记录** —— 若尚未抓到现场，回滚即等于放弃结案。

## 8. 经验教训

1. **「配置莫名被改」先查有没有内核级反作弊 / 安全软件在跑，别当成系统故障。** 这类组件的写入是**设计行为**，症状呈「周期性拉锯 + 改回默认值」；按系统故障排查会一直在错误的层面上打转。
2. **蓝屏转储的排查要覆盖所有可能的目录，不能只按配置读。** 本例中一份关键转储（09-22 那次）此前**从未**出现在配置目录里 —— 只按配置读，就会得「这次蓝屏没留下转储」的错误结论，进而把整个根因分析带偏。
3. **想要「现场抓获」而不是「事后推断」，就得开审核并等下一次复现。** 三条独立证据（值指纹 / 二进制字符串 / 时间窗）能把嫌疑收窄到「某一族模块」，但**收不到具体进程**。**结案判据必须写清楚**：抓到一条带进程名的改写事件才算结案；在此之前，结论只能标为「推断（非确证）」。
4. **与反作弊对抗是错误方向。** 它改回去是设计行为，对着焊只能**降低概率**，不能根除 —— 而且对抗本身可能带来账号风险。正确的目标是**取证 + 规避**，不是「修好它」。
5. **自愈脚本会掩盖问题。** 守卫每次都能「修复成功」，日志看起来一切正常 —— 它让配置错误变得**不可见**，直到某次蓝屏真的丢了转储才暴露。**自愈类脚本必须额外上报「被改写的次数」**，而不是只报「已修复」。
6. **同一个「查不到」背后可能有两个不同的原因。** 本次「转储找不到」既可能是①配置被改写导致落错目录，也可能是②那次蓝屏根本没产生转储 —— 两者的排查路径完全不同，**动手前先分清是哪一种**。

## 9. 已知限制与未决项

1. **改写主体的身份为「推断（非确证）」。** 三条独立证据（值指纹、二进制字符串、时间窗）同时命中的只有该反作弊家族，但**没有任何人亲眼看到它写下那个值**。定案时游戏未在运行，审核装置是事后安装的 —— 这一点必须如实保留。
2. **结案判据（明确写出，避免无限期挂账）**：抓到**至少一条**含 `ProcessName` 的 `4663` 事件 ⇒ 升级为实测并结案。若长期抓不到，应回查审核是否真的生效（SACL 是否被清理、日志是否被轮转、子类审核是否被组策略覆盖）。
3. **守卫的覆盖面有上限。** 巡检周期是 30 分钟，因此「配置错误的窗口」最坏可达 30 分钟；**游戏时段内发生的蓝屏仍可能只有小转储**。这是被接受的代价，不是待修缺陷。
4. **两个转储目录的检查是人工规程，未自动化。** 目前依赖「排查蓝屏时同时看两个目录」这条书面规程；没有做成自动巡检告警。
5. **小转储的信息量低于完整转储。** 落到默认目录的那三份都是小转储（5.35–6.51 MB），只含寄存器与栈，缺少驱动对象与内存现场 —— 对 [bsod-triage.md](bsod-triage.md) 中的根因判定帮助有限。
6. **改写者只动了两个值，但「只动这两个」是本次观测的结论。** 反作弊模块更新后是否扩大改写范围，未做持续监控。
7. **未验证项**：其它厂商的内核级反作弊 / 安全软件是否有同类行为。本文只覆盖已观测到的一族，**不应推广为「所有反作弊都会改转储配置」**。
