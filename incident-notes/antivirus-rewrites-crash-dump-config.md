# 内核级反作弊反复改写系统转储配置

> 路径约定：`<DUMP_DIR>` 指代部署时配置的转储目录（按实际部署替换）。
> 证据分级：本文结论标注为「实测」「推断（非确证）」「待确认」三档，不混写。

## 问题

为蓝屏取证配置了「完整内存转储 → `<DUMP_DIR>`」后，一个每 30 分钟巡检一次的配置守卫持续报告 `REVERTED(CrashDumpEnabled,MinidumpDir) -> re-applying`：两个注册表值被反复改回 Windows 默认（`CrashDumpEnabled=3` 小转储、`MinidumpDir=%SystemRoot%\Minidump`），守卫每次焊回后又被改回去。

**直接后果**：若蓝屏恰好发生在这段「被改写」的窗口内，转储会落在系统默认目录，而按配置去 `<DUMP_DIR>` 找 —— 找不到。

**症状指纹**（用于识别同类问题）：

| 指纹 | 说明 |
| --- | --- |
| 只有特定的两个值被动 | `CrashDumpEnabled` 与 `MinidumpDir`；同键下的 `AutoReboot` / `DumpFile` / `LogEvent` / `Overwrite` / `DumpLogLevel` / `EnableLogFile` 一个都没动 |
| 改回的方向永远是 Windows 默认 | 小转储 ＋ 系统默认目录 |
| 焊回后过一会儿又被改 | 呈周期性拉锯，而非一次性事件 |
| 改写集中在游戏运行时段 | 游戏一退出，改写立即停止 |
| 误导性健康检查 | 守卫脚本每次都会「修复成功」，日志看起来在正常工作 —— **它只证明配置被改过，不证明配置稳定** |

**为什么这个指纹重要**：它把问题从「系统故障」重新归类为「第三方软件的**设计行为**」—— 后者不能靠修系统解决，只能靠规避与取证。

## 原因

带**内核级反作弊**的游戏运行时，其反作弊模块主动改写 `CrashControl` 下的转储配置（本例为 ACE 系），把它改回「小转储 ＋ 系统默认目录」。

反作弊要在内核态抓取崩溃现场（转储模块里可见 `MiniDumpWriteDump`、`Q?MiniDumpType:%d;` 这类字符串），把系统配置固定到它期望的形态是它的设计行为，不是故障。改写 `MinidumpDir` 则是因为小转储的默认落点是 `%SystemRoot%\Minidump`，指回默认值能保证它自己的转储收集路径可预期。

**证据（三条独立线索指向同一族模块）**：

1. **值指纹**：回退现场的注册表快照显示，只有那两个值被改，且改为固定目标值。这排除了「注册表整体被回滚」「配置文件损坏」等假设。
2. **二进制字符串**：反作弊主体模块（签名有效）与同族模块中**同时存在**下列串：`CrashControl`、`CrashDumpEnabled`、`MinidumpDir`、`%SystemRoot%\Minidump`、`%SystemRoot%\MEMORY.DMP`、`MiniDumpWriteDump`。即：这两套模块**有能力**写这两个值，且代码里写死了「默认目录」这个字符串。
3. **时间窗吻合**：全部改写记录都落在该游戏的运行时段，游戏退出后立即停止。

**关键限定（不要越界引用）**：不是「系统被破坏」也不是「配置丢失」（配置每次都被完整写回）；不影响游戏运行；**不建议**为了转储去对抗反作弊。

完整时间线与证据原文见 [`raw/antivirus-rewrites-crash-dump-config-evidence.md`](raw/antivirus-rewrites-crash-dump-config-evidence.md)。

## 方法

方向：**不要试图根除，改为取证 ＋ 规避。** 与反作弊对抗（拦截写入、禁用服务、改模块）存在账号风险，且不属于部署方可以单方面处置的范围。

| # | 措施 | 状态 |
| --- | --- | --- |
| 1 | 保留配置守卫：开机触发 ＋ 每 30 分钟巡检，检测到改写即焊回原值并写日志 | 运行中 |
| 2 | 补捞系统默认目录里的历史转储，逐哈希校验后归档到 `<DUMP_DIR>` | 已完成 |
| 3 | 在 `CrashControl` 上开启注册表审核（SACL ＋ 对象访问子类） | 已安装 |
| 4 | 取证脚本接入守卫巡检，从安全日志解析出改写进程名 ＋ pid | 已就位，等待触发 |
| 5 | 把「蓝屏排查必须同时检查两个转储目录」写入排查规程 | 已落地 |

### 两处实测坑（否则一条现场都抓不到）

| 坑 | 说明 |
| --- | --- |
| 事件 ID 是 `4663` 而非 `4657` | 该键上的写操作记成「对象访问」`4663`；只有值真的变了才会补一条 `4657`，**同值重写只记 `4663`** —— 按 `4657` 过滤会漏掉绡大多数 |
| `ObjectName` 是 `\REGISTRY\MACHINE\SYSTEM\ControlSet001\Control\CrashControl` | **不是** `CurrentControlSet` 那个写法；按后者匹配一条都抓不到 |

### 验证与结案判据

- **配置侧**：守卫日志不再出现 `REVERTED` ⇒ 改写停止（**仅游戏不运行时成立**）。
- **取证侧（结案判据）**：抓到**至少一条**含进程名的 `4663` 事件 ⇒ 把「推断」升级为「实测」并结案。长期抓不到时应回查审核是否真的生效（SACL 是否被清理、日志是否轮转、子类审核是否被组策略覆盖）。
- **下次蓝屏时两个目录都要查**：

```powershell
Get-ChildItem -Path '<DUMP_DIR>', "$env:SystemRoot\Minidump" -Filter *.dmp |
    Sort-Object LastWriteTime -Descending | Select-Object -First 10 FullName, Length, LastWriteTime
```

## 结果

守卫持续运行，配置每次被改写后均被完整写回；归档补齐了历史转储。现场抓获装置已就位但**尚未触发** —— 因此改写主体的身份仍为**推断（非确证）**。

### 回滚

| 项 | 回滚方式 |
| --- | --- |
| 配置守卫脚本 | 停止并注销其计划任务；注册表值不会自动改回，需手工设置 |
| `CrashDumpEnabled` | `Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CrashControl' -Name CrashDumpEnabled -Value 3 -Type DWord` |
| `MinidumpDir` | `Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CrashControl' -Name MinidumpDir -Value '%SystemRoot%\Minidump' -Type ExpandString` |
| 注册表审核 | 按安装前存档（原为 `No Auditing`、原 SACL 为空）还原，或直接移除该键 SACL |
| 归档转储 | 原文件仍在系统默认目录，归档是**拷贝**而非移动，可直接删 |

⚠️ **回滚审核前先确认**：移除 SACL 后已有记录不会被删，但**新的改写事件将不再被记录** —— 尚未抓到现场时，回滚等于放弃结案。

### 可迁移结论

1. **「配置莫名被改」先查有没有内核级反作弊 / 安全软件在跑，别当成系统故障。** 这类写入是设计行为，症状呈「周期性拉锯 ＋ 改回默认值」；按系统故障排查会一直在错误的层面上打转。
2. **蓝屏转储排查要覆盖所有可能目录，不能只按配置读。** 本例一份关键转储此前**从未**出现在配置目录里；只按配置读就会得出「这次蓝屏没留下转储」的错误结论，进而把整个根因分析带偏。
3. **想要「现场抓获」而不是「事后推断」，就得开审核并等下一次复现。** 三条独立线索能把嫌疑收窄到「某一族模块」，但**收不到具体进程**。结案判据必须写清楚；在此之前结论只能标为「推断」。
4. **与反作弊对抗是错误方向。** 目标是**取证 ＋ 规避**，不是「修好它」。
5. **自愈脚本会掩盖问题。** 守卫每次都能「修复成功」，让配置错误变得不可见，直到某次蓝屏真的丢了转储才暴露。**自愈类脚本必须额外上报「被改写的次数」**，而不是只报「已修复」。
6. **同一个「查不到」背后可能有两个不同原因**（配置被改写导致落错目录 / 那次蓝屏根本没产生转储），两者排查路径完全不同，动手前先分清是哪一种。

### 已知限制

1. **改写主体身份为推断（非确证）。** 三条线索同时命中的只有该反作弊家族，但**没有任何人亲眼看到它写下那个值**；定案时游戏未运行，审核是事后安装的。
2. **守卫覆盖面有上限。** 巡检周期 30 分钟 ⇒ 「配置错误窗口」最坏可达 30 分钟，游戏时段内发生的蓝屏仍可能只有小转储。这是被接受的代价，不是待修缺陷。
3. **两个转储目录的检查是人工规程，未自动化。**
4. **小转储信息量低于完整转储**（只有寄存器与栈，缺驱动对象与内存现场），对根因判定帮助有限。
5. **「只动这两个值」是本次观测的结论。** 反作弊模块更新后是否扩大改写范围，未做持续监控。
6. **未验证**：其他厂商的内核级反作弊 / 安全软件是否有同类行为。本文只覆盖已观测到的一族，**不应推广为「所有反作弊都会改转储配置」**。
