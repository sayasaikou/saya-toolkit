> 事故编号：INC-2026-0918-03 ｜ 首次观测：2026-08-26 ｜ 最近一次：2026-09-18 ｜ 状态：**诊断进行中**

## 1. 摘要

在约三周（2026-08-26 至 09-18）的观察窗口内，同一台主机出现了横跨多个互不相关子系统的故障：三次蓝屏分别对应三个不同的 bugcheck 码（`0xE6` DRIVER_VERIFIER_DMA_VIOLATION、`0xCE` DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS、`0x116` VIDEO_TDR_FAILURE），另有四次连 bugcheck 都未能留下的硬冻结 / 意外关机，以及一次 PCIe 可纠正错误与三次非致命内核挂起。

**主要推断（非确证）**：多个互不相关的子系统轮流出错，并伴随「连 bugcheck 都留不下」的硬冻结，属**平台级（硬件 / 固件 / 供电）不稳定**的典型形态，而非单一驱动的缺陷。

已完成处置：开启完整内存转储收集能力、保留硬冻结现场取证入口、清理一组已卸载安全软件遗留的孤儿内核驱动，并挂起 24 小时观察窗。内存混插仍留在嫌疑名单内但权重下降（两次内存测试通过为实证）。

## 2. 现象与症状指纹

**观测到的故障形态**：

| 形态 | 次数 | 特征 |
| --- | --- | --- |
| 蓝屏（有转储） | 3 | 三个互不相同的 bugcheck 码 |
| 意外关机 / 硬冻结（**无转储**） | 4 | 系统日志仅留 Kernel-Power 41 + 6008，无内核现场 |
| PCIe 可纠正错误 | 1 | WHEA-Logger ID 17 |
| 非致命内核挂起 | 3 | 活内核转储（LiveKernelReports） |

**症状指纹**（用于判断是否属同一类问题）：

| 指纹 | 说明 |
| --- | --- |
| **多个不同 bugcheck 码轮番出现** | 单一驱动缺陷通常反复产生同一个码；码不一致指向共享底层（硬件 / 固件 / 供电） |
| **存在无转储的硬冻结** | 连 bugcheck 都未能留下，说明内核未走到崩溃处理路径 |
| 崩溃发生在近乎空载时 | 操作者在崩溃时未运行任何负载程序，机器处于近空转状态仍发生 TDR 蓝屏 |
| 时间跨度 | 早于本次排查，2026-09-02 即已有同类事件 |
| ⚠️ 默认转储配置不足 | `CrashDumpEnabled=3` 仅存小转储（寄存器 + 栈，缺驱动对象与内存现场），不足以定案 |

## 4. 根因（分层判定，含未定案部分）

### 4.1 已排除项（实测）

| 项 | 实测值 | 结论 |
| --- | --- | --- |
| 磁盘 | 两块 NVMe 固态盘：一块标称 1 TB（实报 954 GB）为系统盘，一块标称 2 TB（实报 1908 GB）为数据盘；两者 `HealthStatus=Healthy`、`Wear=0`、温度 60 °C | 已排除 |
| 供电 | `PowerOnline=True`、电量 100 %、未充电未放电 | 交流供电正常 |
| 温度 | 09-18 双烤实测 GPU 69 °C / CPU 78 °C，未越上限（87 / 100 °C）；`Temp limit` 全程 0 次 | 散热非瓶颈 |
| 电池 | 设计容量 87,395 mWh ／ 满充容量 87,672 mWh，健康度约 100 % | 排除电池老化导致的供电不稳 |
| 显卡超频 | 显卡调节工具未套用任何核心 / 显存偏移（`CoreClkBoost` 与 `MemClkBoost` 均为空；`UnlockVoltageControl=0`、`ForceConstantVoltage=0`、`UnofficialOverclockingMode=0`） | 已排除超频因素 |
| 系统版本 | 系统固件版本与日期已记录（出厂固件，非本次事故后的改动） | 见 4.3 |

### 4.2 已确证项

**确证 ①：内存为混插**。测试机为双内存槽机型，两条 DDR5-5600 SO-DIMM 容量均为 16 GB、均为单 Rank（Rank=1），但**来自不同厂商、不同型号**（`Win32_PhysicalMemory` 实测）。经操作者确认：**一条为出厂原装，另一条为自行加装**。

不同厂商 / 不同 die 的 DDR5 混插是已知的稳定性风险源，其症状形态正是「不同 bugcheck 码轮番出现 + 无故硬冻结」。

**确证 ②：一组已卸载安全软件遗留的孤儿内核驱动正在运行**。系统内已不存在该安全软件的本体程序，也查不到卸载记录，但两个内核驱动仍被加载，其中一个是 `BOOT_START` 级别的早启动反恶意软件驱动。详见 4.4 与 6.1。

**确证 ③：`0x116` 崩溃的肇事地址落在 NVIDIA 显示驱动区间内**（实测；但见下方限定）。

**确证 ④：显卡调节工具未套超频**（与 4.1 的表一致，此处仅作结论归档）。

### 4.3 推断（非确证）

**推断 ①：平台级不稳定**。依据见第 3 节末尾。

**推断 ②：内核中并存多组高权限 hooked 驱动，构成故障的背景条件**。崩溃现场加载中的可疑第三方内核驱动、以及一组已卸载安全软件的孤儿驱动（其中之一为早启动级别），加上游戏反作弊驱动、显卡调节驱动、主板厂商驱动等，共同构成「多个互不相关子系统随机出错 + 硬冻结」的常见背景条件。此为背景条件，**不构成对任何单一模块的定罪**。

**推断 ③：内存混插仍在名单，但权重下降**。操作者答复两点实测事实：① 内存测试已全盘跑过两次、无报错；② 其**强制需求 32 GB 容量**，因此「拔掉一条」不能作为长期方案。据此，内存混插由「首要嫌疑」降级为「仍在名单、权重下降」。保留的可能性是：混插仅在**真实负载 / 温度条件**下才暴露（内存测试工具的访问模式与真实负载不同），该假设只能靠**单条 A/B 跑真实负载**排除。

**推断 ④（相关性，非因果）**：孤儿驱动的文件创建时间为 **2026-08-11 12:12:37**，而首轮硬件事件出现在 08-26 / 08-30 —— 两者在时间上相邻，**属相关性，尚无因果证据**。

### 4.4 尚未定案

- 系统固件（BIOS）是否为最新版本尚未确认：现行版本日期为 2026-04-17，且**主板厂商官网当前无法正常访问**（HTTP 403），需要换途径核实。
- 显卡驱动版本为 2026-07-22 发布（距今约两个月），与 `0x116` 直接相关，但在排查顺序上排在内存之后。
- **悬案（明确记录，不编造解释）**：两次崩溃（19:23 的 `0x116` 蓝屏 / 19:28 的硬冻结）**都落在执行上述转储分析动作的时间窗内**（第一次在安装调试工具的包下载段，第二次在符号拉取段）。该调试工具不接触显卡，**既不能证明相关、也不能证明无关**；两者的共同点是**持续的重磁盘 / 网络 I/O**。在内存问题排除前，不自动重跑该类分析。

## 5. 证据链

### 5.1 转储模块表（`091826-17156-01.dmp`：`lm` 与已卸载模块表）

崩溃现场**加载中**的可疑第三方内核驱动：

| 模块 | 地址段 | 归属 |
| --- | --- | --- |
| `BAPIDRV64` | `0xfffff80330e00000`–`0xfffff80330e39000` | 某国产安全套件（已卸载） |
| `RTCore64` | `0xfffff8033e640000`–`0xfffff8033e64a000` | RivaTuner / MSI Afterburner |
| `ACE_CORE302706` | `0xfffff8033e730000`–`0xfffff803445a0000`（约 99 MB） | 腾讯 ACE 反作弊 |
| `MsIo64` | `0xfffff80330d60000`–`0xfffff80330d6b000` | MICSYS（主板厂商自带） |
| `Nahimic_Mirroring` / `NahimicBTLink` | — | MSI Nahimic |

已卸载但留痕的模块（模块表中的卸载残留项）：`360elam64.sy`、`ACE-SSC-DRV6`、`ACE-ADVT.sys`、`ace-game-0.s`、`ACE-CORE1027`、`ACE-CORE2027`、`ACE-GAME.sys`、`RTCore64.sys` ×2、`GPU-Z-v8.sys`、`kerneld-x64.`。

**bugcheck 参数定位（实测）**：`nt` 基址为 `0xfffff80386400000`；arg2 = `0xfffff80333a6a350`，**落在 `nvlddmkm` 区间 `0xfffff80332110000`–`0xfffff80339485000` 之内**（偏移 +0x195a350），即 `0x116` 的「肇事地址」指向 NVIDIA 显示驱动。

> ⚠️ **限定**：TDR 按定义就归因于显示驱动，因此该地址**不构成定罪**；它只说明崩溃现场位于显示驱动代码路径上。

### 5.2 已卸载安全软件的孤儿内核驱动（实测）

系统内已无该安全软件的本体程序，也无卸载记录，但下列内核对象仍在：

- 服务 `BAPIDRV`：`Start=1`（`SYSTEM_START`）、**`State=RUNNING`**、`system32\DRIVERS\BAPIDRV64.sys`（229,128 B，签名有效）—— **转储证据证实崩溃时该驱动就在内核内存中**。
- 服务 `360elam64`：`Start=0`（**`BOOT_START`**）、`Group=Early-Launch`、`system32\DRIVERS\360elam64.sys`（18,048 B）—— **早启动反恶意软件驱动，在系统启动极早期加载**。
- 目录残留：`%ProgramFiles(x86)%\360\360Safe\{deepscan,ipc,safemon}`、`%APPDATA%\360safe`。
- 注册表项：`HKCU\SOFTWARE\360`、`360DayPop`、`360Newsld`。
- **无相关进程、无卸载记录** ⇒ 判定为**卸载残留的孤儿内核驱动**。

### 5.3 图形调节工具的洗清（本排查过程中被自身证据推翻的假设）

- 安装于数据盘（显卡调节工具 4.6.6 ＋ 统计服务器 7.3.7）；**不在任何 Run 启动项、无相关计划任务**（配置中 `StartupViaTaskScheduler=1`，但对应任务不存在）。
- 显卡配置文件（按 `VEN_10DE&DEV_2C19` 命名）：`CoreClkBoost=`（空）、`MemClkBoost=`（空）→ **未套用任何核心 / 显存偏移**。
- `UnlockVoltageControl=0`、`ForceConstantVoltage=0`、`UnofficialOverclockingMode=0` → 未做降压 / 解锁。
- `RTCore64` 被加载的原因 ＝ 当天使用过调节工具 / 硬件信息工具读取传感器（14:04 有配置文件写入），**与超频无关**。

### 6.2 验证方式与判据

- **重启后观察 24 小时**：若不再出现蓝屏 / 硬冻结 ⇒ 该组孤儿驱动为主要成因（或主要成因之一）。
- 若**仍然崩溃** ⇒ 该组孤儿驱动不是主因，按剩余嫌疑继续排查：内存混插（单条 A/B 跑真实负载）→ 显卡驱动（2026-07-22 版本）→ 系统固件（2026-04-17 版本）→ 显卡 / 供电硬件。

## 8. 经验教训

1. **结论必须分档留痕**。本次排查同时存在实测、推断与待确认三类信息，混写会让后续引用把推断当成实证。分档之后，「内存混插」这类曾被列为首要嫌疑、后被降权的项才不会被误当作定案。
2. **默认转储配置往往不足以定案**。`CrashDumpEnabled=3` 只保留小转储，缺少驱动对象与内存现场；在没有开启完整转储之前，「分析转储」这条路本身是走不通的。
3. **批量删除前必须逐条检视命中项**。按关键字匹配会把名称近似的系统自带组件一并卷进来（本例 `bapi` 命中 `cabapi.dll` / `dabapi.dll`）；只看命中数量、不看命中内容，迟早误删系统组件。
4. **已卸载软件的残留内核驱动是真实存在的风险面**，尤其是早启动（`BOOT_START`）级别的反恶意软件驱动：本体已不存在，驱动仍在每次开机极早期加载，且不会被常规卸载流程清理。
5. **排查动作本身要避开高风险时间窗**。在根因未定（尤其是内存未排除）时执行持续重 I/O 的分析任务，会污染现场，使「动作」与「故障」在时间上纠缠、难以定性。
6. **症状形态本身是证据**。「多个不同 bugcheck 码 + 无转储硬冻结」这一组合，比任何单个转储更早地指向平台级不稳定；它决定了排查顺序应当从平台（内存 / 固件 / 供电）开始，而非从某个具体驱动开始。
