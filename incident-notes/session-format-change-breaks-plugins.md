# 事故复盘：宿主会话格式变更导致全部插件加载失败

## 1. 摘要

宿主应用发布了一个大版本，其中**会话日志格式发生结构性变更**。读取该格式的插件仍按旧结构解析，在启动阶段抛异常，导致**整个插件层加载失败**、界面显示「插件加载失败」。

本事故的价值不在于「升级要小心」，而在于它的**症状与检查结果互相矛盾**：所有静态检查都是绿的 —— 配置文件正确、插件文件齐全、加载清单无缺失 —— 只有运行期解析失败。这类故障用「检查文件在不在」的办法永远查不出来。

## 2. 现象与症状指纹

**表现特征**

- 界面报「插件加载失败」（或同类整体性错误），**不是某一个插件坏掉**，而是整层不工作。
- 宿主本体能起来，服务在线，端口正常。
- 卸载/重装插件无效（重新安装的是同一份代码，解析逻辑没变）。
- 冷启动必现，不是偶发。

**注意： 会给出误导性结论的检查**

| 检查手段 | 结果 | 为什么不可信 |
| --- | --- | --- |
| 检查插件文件是否存在 | 全部存在 | 文件在不在与解析成不成功无关 |
| 检查配置文件语法 | 正确 | 配置没问题，问题在数据解析 |
| 检查加载清单 / boot manifest | 无缺失 | **清单反映的是「声明要加载什么」，不是「加载成功了什么」** |
| 重新安装插件 | 无效 | 同一份代码配同一种新数据，必然同样失败 |
| 查看「插件已启用」的界面提示 | 显示正常 | 声明层面的状态，不是运行期状态 |

**唯一有效的信号是运行期日志里的异常栈**，以及「**连本应正常工作的旧插件也一起挂了**」这个整体性特征 —— 单个插件坏掉是插件的问题，**全部一起坏掉是宿主契约变了**。

## 3. 时间线

| 阶段 | 事件 |
| --- | --- |
| 变更前 | 插件层正常，所有插件按旧格式读取会话数据 |
| 宿主升级 | 宿主发布大版本，会话存储格式同步变更 |
| 首次启动 | 插件层整体加载失败，界面报错 |
| 排查 | 逐项检查配置文件、插件文件、加载清单 —— **全部正常**，与现象矛盾 |
| 定位 | 读运行期异常栈，发现失败点在**解析会话数据结构的代码**上，对不存在的字段取属性 |
| 修复 | 读取侧改为**同时兼容新旧两种结构** |
| 验证 | 冷启动后插件层恢复；人格/注入类插件的脚印文件时间戳推进（说明它真的跑到了） |

## 4. 根因

**契约变更没有伴随兼容层。** 宿主侧把会话记录的结构改成了嵌套更深的形态；插件侧原本假设某个键直接存在于顶层对象上。旧数据下这个假设成立，新数据下该键位于嵌套位置（或在某些记录里根本不存在），于是取到 `undefined`，再对它取属性即抛异常。

关键机制：**这个异常发生在插件注册/初始化的早期阶段**。多数插件宿主在加载期遇到未捕获异常时会**放弃整个插件层**，而不是仅仅跳过出错的插件 —— 这就是「一个插件解析失败 → 全部插件不工作」的放大路径。

由此得出两条可迁移结论：

1. **「加载清单正常」不等于「插件加载成功」。** 清单是声明，运行期才有事实。要证明插件真的起来了，得看它自己留下的痕迹（脚印文件、日志行、注册成功记录），而不是看配置或清单。
2. **读取外部数据结构时，对不存在的字段要能容忍。** 尤其是在你自己不控制格式演进方向的时候 —— 那不是防御性编程，那是这个依赖关系的正常成本。

## 5. 证据链

1. **运行期异常栈**：失败位置在解析会话数据、访问某个字段属性的那一行，类型为「无法读取 undefined 的属性」。这是唯一定位到根因的证据；其余检查都是排除法。
2. **整体性失败特征**：多个互不相关的插件同时失效 ⇒ 排除「某个插件自身的问题」，指向共享的上游契约。
3. **新旧数据对照**：同一段解析代码，喂旧结构数据通过、喂新结构数据抛错 ⇒ 确认是结构假设失效，不是数据损坏。
4. **修复后的正向证据**：冷启动后插件层恢复；**注入类插件的脚印文件时间戳向前推进** —— 这是「它真的执行过」的凭据，比界面提示可靠。

## 6. 修复措施与验证

**修复方向：读取侧写双形态兼容，而不是把数据改回旧格式**（改数据等于放弃升级；兼容读取是一次性成本）。

具体做法：

1. 解析时**先探测结构形态**（判断关键字段在哪一层），再走对应分支；
2. 对缺失字段给默认值，保证任何一条历史记录都不会让整批解析失败；
3. **对同一份代码喂两套形态的数据各跑一次测试** —— 这是本轮唯一能防止复发的验证手段。

**验证清单（顺序即优先级）**

| # | 验证项 | 判据 |
| --- | --- | --- |
| 1 | 冷启动（不是热重载） | 插件层恢复，无加载失败提示 |
| 2 | 插件脚印文件 | 时间戳**推进**（证明插件真的执行过，而非只是被声明） |
| 3 | 新旧两套数据各跑一次 | 都通过 |
| 4 | 加载清单 | 仍然无缺失（回归确认） |

## 7. 回滚方案

- **回滚宿主版本**：需要保留升级前的安装包与用户数据目录。注意： 注意：**新格式的会话数据可能无法被旧版本读取** —— 回滚宿主不等于回滚数据，回滚前先确认数据向后兼容性，或者接受丢失升级后产生的会话。
- **临时旁路**：停用读取会话数据的插件，让宿主先跑起来（牺牲功能换可用性）。
- **本事故的最佳回滚点是「升级前对用户数据目录做一次完整快照」** —— 这类跨版本格式变更，事后补备份是来不及的。

## 8. 经验教训

1. **「文件都在」不是证据。** 静态完整性检查（文件存在、配置合法、清单完整）只能排除一类故障；**运行期契约变更根本不在它的覆盖范围内**。判断「某个组件是否真的工作了」时，要找它**主动留下的痕迹**，而不是找它**应该存在的文件**。
2. **全部一起坏 ⇒ 看上游契约，不要逐个修下游。** 多个互不相关的组件同时失效，几乎总是共享依赖变了。
3. **插件宿主应当隔离加载失败。** 一个插件初始化失败就拖垮整层，是把小故障放大成大故障的设计。若宿主不提供隔离，插件侧就更要保证**初始化路径不抛异常**（把可能失败的逻辑推迟到第一次实际使用）。
4. **对不属于自己的数据结构保持宽容。** 字段可能不存在、可能换层、可能是历史遗留形态 —— 读取方都要能活下来。
5. **升级大版本前先快照用户数据。** 这条的成本是几分钟，收益是「能不能回去」。

## 9. 已知限制与未决项

1. **本复盘描述的是失败机制与排查路径，不针对特定宿主的特定版本** —— 任何「插件读宿主私有格式」的架构都可能复现同一类事故。
2. **兼容读取有长期成本**：每支持一种历史形态就多一条分支。当确认旧形态数据已不再存在时，应当**显式移除**兼容分支并记录移除依据，否则代码里会积累一批没人敢删的分支。
3. **未验证的部分**：不同的插件宿主对「加载期异常」的处理策略不同（有的整层放弃、有的只跳过出错项）。本事故中表现为整层失败，**换一个宿主可能只是部分功能失效** —— 症状会变，但根因判据（整体性 vs 单点）依然适用。
4. **没有做跨版本矩阵测试**（多宿主版本 × 多数据形态），只验证了两种形态的端点。
