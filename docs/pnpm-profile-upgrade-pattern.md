# 在活的 profile 里做包管理操作会炸：两段式升级模式

适用：任何“运行中的应用目录 + pnpm 管理依赖 + 目录是从别的实例拷来的”场景。

## 问题

在**正在运行**的 profile 目录里直接执行 `pnpm add` / `pnpm install`，会出现两种失败：

| 现象 | 说明 |
| --- | --- |
| `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE` | 每次 `pnpm add` 都失败，且失败前已经改写了部分清单文件 |
| `pnpm install` 挂死 | 修完上一个之后紧接着发生，本次实测挂了 **3 小时 42 分**没有返回 |

**误导性信号**：目录里 `package.json` / `pnpm-lock.yaml` 看上去都正常，`node_modules` 也完整存在 —— 静态看一切都对，只有真正跑 pnpm 才会炸。

## 原因

**virtual store 的元数据与目录实际情况不一致。**

该目录的 `node_modules` 是从**另一个实例**（另一个 profile）拷贝而来的。pnpm 把“真实存储在哪”写在 `node_modules/.modules.yaml` 里：

- 拷贝过来的 `.modules.yaml` 仍指向**源实例的** `.pnpm` 目录；
- 它声明的 pnpm 版本也与当前运行时**不同**（实测：声明 12.x，运行时为 11.x）。

pnpm 启动时校验这层元数据，一旦不符就拒绝操作。而 `pnpm install` 挂死，是因为它在这个不一致的 store 上尝试重建依赖图，又碰上了元数据声明的版本与实际工具链的差异。

⇒ **根因不是“依赖装坏了”，而是“这棵目录不是由本机的 pnpm 建立的”。** 拷目录这种迁移方式必然留下这个隐患。

## 方法

**不要在活目录上修。在它旁边重新建一棵树，建好之后再换过去。**

```
第一阶段（应用可以继续跑，无停机）
  <home>/profiles/_build/            <- 从活 profile 拷四个种子文件
  pnpm --dir <home>/profiles/_build install        （秒级，全部来自本地 store）
  pnpm --dir <home>/profiles/_build add <pkg>@<ver>

第二阶段（唯一停机点：停应用 -> 两次改目录名 -> 起应用）
  把 _build 换成活 profile，旧目录留在旁边当回滚点，失败则自动改回
```

**四个种子文件**：`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`.npmrc`（缺任何一个都会让构建树与活树不同源）。

### 三个必须遵守的细节

1. **不要给已经装有目标的构建树重新播种。** `pnpm add` 会改写构建树自己的清单；从活 profile 再拷一次种子会**盖掉已构建的结果**，第二阶段又把这份被盖的结果带回去。
2. **构建树需要“种子漂移”预检。** 上一次会话遗留的构建树可能带着**不同的目标集**；直接往上加包，会把两批不同来源的变更混到同一棵树里。预检不通过就删掉重建。
3. **免年龄限制的配置里，一个包名只能有一条规则。** 写成多行时，只有第一条生效，后面的看着像豁免、实际不生效，而报错会在完全不同的地方出现（详见 `win-agent-tools/normalize-release-age.mjs`）。

### 验证（顺序即优先级）

| # | 验证项 | 判据 |
| --- | --- | --- |
| 1 | 第一阶段结束后 | 构建树里目标包的版本号 = 期望值 |
| 2 | 第二阶段结束后 | 应用能重新启动，且功能正常 |
| 3 | 插件能否真加载 | **看它自己留下的脚印（时间戳/日志），而不是看配置文件或加载清单** |
| 4 | 失败时 | 旧目录已改回原位，应用能起来 |

## 结果

实测多轮、共二十余次包升级，停机时间稳定在 **2~9 秒**；失败时自动回滚，没丢过环境。

第一阶段可以随时重跑（幂等），所以“先构建、稍后换”这个拆分本身把风险降到了“换名字”这一步。

### 可迁移结论

1. **拷贝来的 `node_modules` 不能算“装好了”。** 先向包管理器问一次“这个 store 是不是你的”，再决定要不要在上面操作。
2. **把“耗时/可能失败”的部分和“影响可用性”的部分拆开。** 前者放在旁边慢慢干，后者压缩成两次目录改名 —— 这个拆分比任何“小心操作”都可靠。
3. **构建树与活目录的清单会合法地不同**（因为前者被安装过程改写过）⇒ 不能拿“两边一致”当健康判据，要拿“目标版本对不对”当判据。
4. **挂死比报错危险。** 同样一个元数据不一致，有的命令报错（能定位），有的挂三小时（看着像卡）。给这类操作加超时，而不是相信它会自己结束。

### 已知限制

- 本模式假定应用支持“停一下再起”且目录可改名；不支持热插拔的场景需要额外的切流方案。
- 停机时间取决于应用启动速度，与包数量无关。
- “拷目录”这个前提一旦去掉（改为目标机器上原生安装），本文描述的两个失败模式都不存在 —— 真正该修的是迁移方式。
