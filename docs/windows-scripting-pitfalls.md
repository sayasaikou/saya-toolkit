# Windows 自动化脚本实操坑（路径 · 计划任务 · 编码 · 句柄 · 长任务）

> 本文收录长期运维中反复踩到的 Windows 脚本陷阱。每条都写明**现象 → 机制 → 处置**，并标注证据级别。
> **证据分级**：「实测」＝本次或原现场有可复核输出；「现场记录」＝真实发生过但触发条件未完全复现；「机制推断」＝由已知机制推出，未直接验证。
> 与本文配套的编码 / 引擎差异详见 [`powershell-cross-engine-guardrails.md`](powershell-cross-engine-guardrails.md)。

## 1. 路径与参数

### 1.1 中文 + 空格路径经 `Start-Process -ArgumentList` 会被截断

```powershell
Start-Process -FilePath 'cmd.exe' -ArgumentList '/c', $script, 'D:\my workspace\out'
# 实测：目标进程收到的是 D:\my —— 空格后半段被当成下一个参数
```

**机制**：`-ArgumentList` 是字符串数组，最终仍要拼成一条命令行。带空格的元素没有被引号包住，接收方按空格切分。

**处置**（按可靠性排序）：

1. **把路径写进 ASCII 脚本内部**，调用时只传纯 ASCII 的参数；
2. 只传纯 ASCII 的目录名，由脚本自己拼完整路径；
3. 确实必须传路径时，显式加引号并确认目标程序的引号解析规则 —— 不同程序（尤其是 `cmd.exe` 与自研 exe）规则不同，不可想当然。

**验证方式**：写一个只回显 `$args` 的小脚本做接收端，先确认参数原样到达，再接真实逻辑。

### 1.2 PowerShell 数组字面量拼接坑：`+` 与 `,` 的优先级

```powershell
$D = 'D:\data'
$list = @($D + '\a', $D + '\b')
# ❌ 实测结果是一条字符串：D:\data\aD:\data\b
```

**机制**：逗号的优先级**高于** `+`。上面被解析为 `$D + ('\a', $D) + '\b'` —— 中间的数组在与字符串相加时被强制转换并拼接，于是两个元素粘成一条。

**处置**：一律用 `Join-Path` 逐条追加，既避开优先级坑，也避开手工拼分隔符：

```powershell
$list = @()
$list += Join-Path $D 'a'
$list += Join-Path $D 'b'
```

### 1.3 `List[string].AddRange($objectArray)` 会抛类型转换异常

```powershell
$l = New-Object System.Collections.Generic.List[string]
$l.AddRange($someObjectArray)   # ❌ Object[] 不会自动转成 IEnumerable[string]
```

**处置**：`foreach` 逐条 `Add`，或先 `[string[]]` 强转。

```powershell
foreach ($item in $someObjectArray) { $l.Add([string]$item) }
```

### 1.4 函数要返回数组时写 `return ,$arr`

PowerShell 在返回时会**解包集合**：返回单个元素的数组会变成标量，返回空数组会变成 `$null`。一元逗号包一层可保住数组语义：

```powershell
function Get-Items { return ,$items }   # 调用方拿到的始终是数组
```

### 1.5 教训：改长文件先写临时文件 + 回读校验，再覆盖原文件

上面 1.2 / 1.3 / 1.4 三条在同一天内被连续踩中，其中一次直接把一份长状态文件写坏（有备份、零信息损失，但白跑一轮）。

**固化为纪律**：

1. 先把结果写入**临时文件**；
2. **回读临时文件**并校验结构性标记的数量（如分区注释标记成对出现、条目数吻合）；
3. 校验通过后才覆盖原文件；
4. 覆盖前保留 `.bak-<时间戳>`。

> 判据是**回读**，不是「脚本打印了成功」。脚本自己打印的字不构成证据。

## 2. 计划任务

### 2.1 设完必须回读 `NextRunTime` + `State`

注册成功 ≠ 设上了。必须回读：

```powershell
$t = Get-ScheduledTask -TaskName '<TASK>'
$i = Get-ScheduledTaskInfo -TaskName '<TASK>'
$t.State          # 期望 Ready（不是在运行、不是 Disabled）
$i.NextRunTime    # 期望是预期的未来时刻
$i.LastTaskResult # 手动触发一次后应检查
```

⚠️ **别在任务自己的运行实例里读自己的 `State`** —— 会把「已禁用」读成 `Running`。真实状态一律用**外部会话**读。

### 2.2 `schtasks /change` 的 `/tr` 嵌套引号会翻车

`/tr` 的值本身要带引号，路径里再带空格或引号时，转义层次迅速失控。**改用 `Register-ScheduledTask`**，参数是结构化的，不走命令行解析。

修改已有任务时，**不要重建任务对象**（会丢运行级别、用户上下文与触发器配置）。正确姿势是导出 XML → 改 → 导入：

```powershell
$xml = Export-ScheduledTask -TaskName '<TASK>'
# 修改 $xml 后：
Register-ScheduledTask -Xml $xml -TaskName '<TASK>' -Force
```

### 2.3 任务动作别用裸 `cmd`

用裸 `cmd.exe` 作任务动作会**弹出一个可见的控制台窗口并一直挂着**。操作者会把它点掉 —— 而点掉窗口**会把脚本一起杀掉**（实测：一次排队重启的验证脚本就死在这里）。

**处置**：用 **GUI 子系统**的无窗口启动器承载（`run-hidden.exe` / 自行编译的 GUI 子系统 PE）。注意：

- 仅设 `-WindowStyle Hidden` **不能**避免窗口创建与焦点抢占；
- `CREATE_NO_WINDOW` 只作用于**子进程**，不作用于自身 —— 自己是控制台子系统程序时照样弹窗。

### 2.4 `schtasks` 的输出是本地化的

中文系统下 `schtasks /query` 输出的字段名是中文（「任务名 / 状态 / 下次运行时间」），而助手会话里的 `pwsh` 可能输出英文 —— **同一段解析脚本两边结果不同**。

**处置**：脚本**不要按英文标签匹配**。用**任务名 + 结构化 API**（`Get-ScheduledTask` / `Get-ScheduledTaskInfo`）取字段；确需解析文本时，做中英文别名映射。

### 2.5 日志不能让计划任务的 shell 重定向来写

`*>` 之类的重定向**在任务动作里不落盘**（实测：任务跑完，日志文件根本没出现）。

**处置**：让脚本**自己追加写日志文件**（`Add-Content` / `Out-File -Append`），并在脚本入口第一行就写好日志路径。

### 2.6 `RepetitionDuration` 不能用 `[TimeSpan]::MaxValue`

序列化后会变成 `P99999999DT...` 这种非法时长，**注册直接失败**。

**处置**：用一个足够大的有限值，例如 **3650 天**。

### 2.7 ⚠️ 只读任务别给 `RunLevel Highest`

巡检、核对、状态回读这类**只读**任务没有任何提权需求。给它们 `Highest` 只会扩大攻击面，并在非提权会话里直接导致注册失败（见 2.9）。

### 2.8 一次性任务用完必须注销

临时任务（重启服务、排队执行、一次性修复）干完活要 `Unregister-ScheduledTask`，**别留残渣**。

⚠️ **已知边界**：「注销正在运行的那个任务自己」会被排到任务结束之后执行 —— 现象是每次清理都剩一个新任务。

**姿势**：注册一个新任务去注销旧任务，再从会话里注销「正在跑的那个」。

### 2.9 从非提权会话注册 `Highest` 任务会直接「拒绝访问」

**判据：先看目标进程跑在谁的令牌下，别照抄别人的做法。**

| 目标进程的令牌 | 需要的 `RunLevel` |
| --- | --- |
| 非提权（普通用户启动） | **`Limited` 就够** —— 同一用户、同完整性级别，依然杀得掉它 |
| 提权 | 需要 `Highest`；而**从非提权会话注册 `Highest` 任务会被系统直接拒绝** |

这条在不同部署下结论相反，因此**不能沿用他人经验**：先 `whoami /priv` / 看进程的完整性级别，再决定 `RunLevel`。

## 3. 编码

### 3.1 ⚠️ `Set-Content -Encoding UTF8` 的语义在两个引擎间变了

| 引擎 | 写出的文件 |
| --- | --- |
| pwsh 7 | **无 BOM**（实测首 3 字节 `68 65 6C`） |
| powershell.exe 5.1 | **带 BOM**（实测首 3 字节 `EF BB BF`） |

同一条命令产出不同字节。**跨引擎的「A 写 B 读」链路必须显式指定 BOM 的有无**，不能依赖默认值。

### 3.2 给文件补 BOM 用 .NET

```powershell
$f   = '<文件路径>'
$txt = [IO.File]::ReadAllText($f, [Text.Encoding]::UTF8)
[IO.File]::WriteAllText($f, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

校验（必须做）：

```powershell
$b = [IO.File]::ReadAllBytes($f)
($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)
```

> **为什么必须校验**：不少编辑工具 / 补丁脚本 / 写盘 API 保存时会**静默吃掉 BOM**。改完不检查，下一次计划任务就会以「Result=1、无日志」的形态炸掉。

### 3.3 `-Encoding Byte` 在 7 里要写 `-AsByteStream`

```powershell
# 5.1：可用（实测返回 120）
Get-Content -LiteralPath $f -Encoding Byte -TotalCount 1
# 7：报 'Byte' is not a supported encoding name
Get-Content -LiteralPath $f -AsByteStream -TotalCount 1
```

### 3.4 写 `.bat` 的标准姿势

```powershell
[IO.File]::WriteAllText($p, ($lines -join "`r`n") + "`r`n", (New-Object Text.UTF8Encoding($false)))
```

要点：**显式 CRLF**（`-join "`r`n"`，不要靠编辑器默认）、**无 BOM**。

### 3.5 读清单 / 配置里的中文路径

不要把中文路径当命令参数传（详见配套文档第 4 节规则 5）。把它写进 UTF-8 清单文件，用**纯 ASCII** 脚本按 UTF-8 读：

```powershell
$paths = [IO.File]::ReadAllLines($listFile, [Text.Encoding]::UTF8)
```

## 4. 文件与进程

### 4.1 「能往文件夹里写文件、但删不掉、连改名都失败」⇒ 有进程握着**目录本身**的句柄

这不是 ACL 权限问题，**别在权限和注册表上瞎试**。

**判据**：**能写入**说明写权限没问题；**删不掉 + 改名也失败**说明有进程持有该目录的句柄。

**定位工具**：Sysinternals `handle64.exe`

```powershell
handle64.exe /accepteula -nobanner -a -u "<关键字>"
# 输出：进程名  pid  类型  句柄  路径
```

**三个实测坑**：

1. **它只认「已存在的路径」** —— 查之前先 `Test-Path` 确认目标还在；
2. **输出里的中文会变成 `?`**（ANSI 转换）⇒ **查询关键字用 ASCII**（例如查盘符 + 英文目录名，再人工筛）；
3. **别自己写 `NtQuerySystemInformation` 去解 `SYSTEM_HANDLE_TABLE_ENTRY_INFO_EX`** —— 结构体大小（32 / 40 字节）与字段偏移极易写错，直接用官方工具。

另：**脚本里不能用 `$pid` 当变量名**（PowerShell 只读变量）。

### 4.2 实测案例：音乐播放器长期握住「系统已知文件夹」的目录句柄

某主流音乐播放器客户端（进程名形如 `cloudmusic.exe`；主进程 / 渲染进程 / GPU 进程**三个都持有**句柄）会长期握住「系统已知文件夹」的**目录**句柄。关键事实：

- **与它自己的下载 / 缓存设置无关**（实测该客户端的设置里根本没有那个被占用的路径）；
- **对照实验**：在改动系统下载路径**之前**它已启动 → 握着**旧路径**不放 → 这就是「文件夹删不掉」的真凶；重启该客户端后立刻改握**新路径**；
- 它**不**抓任意文件夹，也不抓工作区里的子目录（探针实测）；
- **关掉它，句柄立刻释放**（实测 0 秒）。

**处置顺序**：删不掉 / 移不动的目录 → 先看有没有这类常驻客户端在跑 → 有就关掉再操作。

### 4.3 判活要看**端口与心跳**，别认 pid

服务进程的 pid 会被**静默换掉**（实测：pid 换了、看门狗照样报 UP）。

**正确判据**：

- 端口是否在监听（连续多次采样）；
- 心跳文件 / 进程启动时间是否前进；
- ⚠️ 同一个服务可能**故意监听第二个端口**（与主端口同 pid、同响应）—— **别当孤儿进程杀掉**。

同理：**别拿日志文件的 mtime 当「服务死了」的证据** —— 日志会长时间不更新而服务完全正常。

### 4.4 升级 / 重装会冲掉客户端补丁

对已发布产物打过的**文件级补丁**（改写客户端 bundle、硬编码路径替换等），会在**升级、重装、依赖包升级**后被整包覆写。

**处置**：

1. 打补丁前**先备份**（`.bak-<时间戳>`），并记录回滚点；
2. 补丁必须**幂等**（重复施加不产生重复插入）；
3. 补丁脚本自带**语法校验**，不过就拒绝写入；
4. 升级后**重新施加并回读**（检查标记命中数，而不是相信脚本打印的「已应用」）；
5. ⚠️ **语法校验只查语法**，查不出运行期错误（未定义引用、暂时性死区等）—— 关键补丁需要额外的运行期验证或自检脚本兜底。

## 5. 跑长任务

### 5.1 独立进程后台跑 + PID 文件 + 内置防重复启动

长任务不要挂在会话进程下（会话结束即被杀）。标准结构：

1. 以**独立进程**启动（`Start-Process` / GUI 子系统启动器）；
2. 启动时写 **PID 文件**；
3. **入口处检查 PID 文件**：进程仍活着就直接退出（防重复启动），并据此实现「续跑」。

### 5.2 中断后续跑，要能识别「正在写、内容残缺」的最后一帧

崩溃 / 断电往往停在写第 N 帧的中途。续跑逻辑必须能判定**最后一帧是否完整**，不完整就**主动删掉重跑**（代价是重做一帧，远小于交出一份坏产物）。

判据示例：帧文件大小与预期不符、缺尾部校验标记、临时文件名未改名完成。

### 5.3 ⚠️ 别用单一指标断定进程死了

**实测反例**：某下载任务的日志里，blob 长度**停住 60 秒零增长**，看起来完全像卡死；实际是它在**写 manifest + 做校验**，命令最终 `exit=0` 正常结束。

**正确判据**：**看命令是否真的退出**（进程是否存在、退出码是多少），而不是看某个中间指标是否在动。

**推论**：给长任务设「无输出超时」时，超时阈值必须留足校验 / 收尾阶段的余量；宁可长一点，也不要误杀正在收尾的任务。

## 6. 已知限制与未复现项

1. **§1.1 的参数截断只在 `Start-Process -ArgumentList` 这一条路径上实测**。其它调用方式（`&` 调用运算符、`cmd /c` 拼接、`schtasks` 动作）的引号规则不同，须各自确认。
2. **§2.9 的 `RunLevel` 结论随部署变化**。同一台机器上，服务以提权 / 非提权启动时结论相反（本机两种情形都遇到过）。**必须每次实测目标进程的令牌**，本文不能替代判断。
3. **§4.2 的句柄案例来自单一客户端的一个版本**，机制（长期持有系统已知文件夹的目录句柄）是否在其它版本 / 其它同类软件上成立未验证。
4. **§5.3 的 60 秒零增长是单次观测**，不构成「凡零增长必未死」的结论 —— 只是提醒不要以单一指标下死亡判定。
5. **本文未覆盖**：WMI / CIM 查询在目标机器上的权限差异、服务账户与交互式会话的路径解析差异（`%APPDATA%` 指向不同）、以及杀毒 / 反作弊类内核组件对脚本行为的干扰（后者见 [`../incident-notes/antivirus-rewrites-crash-dump-config.md`](../incident-notes/antivirus-rewrites-crash-dump-config.md)）。
